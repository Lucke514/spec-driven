# Spec-Driven Development

Write the spec before the code. The spec — not the conversation — is the source of truth for what is being built, why, and how you will know it is done. Code is the output generated *against* the spec, every phase produces an artifact on disk that survives the session, and nothing ships without passing the quality gates and leaving documentation behind.

## Core rules

1. **No implementation before an approved spec.** If the user asks to build something non-trivial and no spec exists, start at Phase 1 (Phase 0 if the request is Large) — do not start coding.
2. **Stop for human review between phases.** Present each artifact (spec, plan, tasks) and get explicit approval before moving to the next phase. The spec's review stop is Phase 2's exit — Phases 1–2 are one unit, so never ask for approval while `[NEEDS CLARIFICATION]` markers remain. Never chain spec → plan → tasks → code in one uninterrupted run. Set an artifact's Status to `in-review` when you present it, and to `approved` once the user signs off; if the user requests changes, revise and re-present — it stays `in-review` until sign-off. The user may explicitly waive the review stops ("run the remaining phases without asking me"): record the waiver as a Decisions entry in `spec.md` and mark the affected artifacts `approved` on that standing instruction — every artifact is still written and presented, just not blocked on. A waiver covers only review stops for work inside the approved scope; adding or changing an `R#`/`E#`, resolving spec drift, implementing a Phase 7 deletion gap, adding a third-party dependency or changing the version of one other code shares, executing a data change the plan records as irreversible or data-losing, executing a delivery step (deploy, promotion between rollout stages, flag change, config change) against a shared, staging, or production environment, removing, disabling, or weakening a pre-existing test, accepting a requirement as a documented limitation, annotating one **superseded**, deferring a requirement out of this change set, and accepting a manual verification as a requirement's only evidence always need explicit sign-off. An approval-gated item whose signer the spec's **Sign-off** line names as someone other than the person in this session is not approved by that person's answer: record it on the spec's Status line as `pending sign-off: <role>`, do not start the work it gates, and never let a waiver — standing or otherwise — cover it.
3. **Artifacts live in the user's repo**, under `specs/<feature-slug>/` (slug: short, lowercase, hyphen-separated, unique across the repo, stable for the feature's lifetime — it also names the branch, the commit prefix `<slug>: `, and `docs/<slug>.md`):
   ```
   specs/
   └── user-authentication/
       ├── spec.md      # what & why — requirements, acceptance criteria
       ├── plan.md      # how — architecture, components, risks
       └── tasks.md     # work breakdown with per-task verification
   ```
   In a monorepo, place `specs/` and `docs/` at the root of the package or app that owns the code — not the repo root — and keep them siblings so the templates' relative links resolve. If no single package owns the feature, put them at the repo root (or the shared/platform package) and list the affected packages in the plan's Current state. Whenever a phase edits an artifact — task checkboxes and completion notes, amendments, Status changes, appended verification reports — set that artifact's `Last updated` to the current date.
4. **Requirements must be testable.** Every requirement in the spec is written so that a reviewer can answer "done or not done?" with a yes/no. Rewrite vague asks ("fast", "user-friendly", "secure") as measurable criteria.
5. **When the spec and the code disagree, the spec wins** — either fix the code, or change the spec explicitly with the user's approval. Never let them drift silently.
6. **No junk code — ever.** A task is not done while its diff contains dead code, debug leftovers, or duplication. The full checklist and gates are in [references/clean-code.md](references/clean-code.md) — requirements, not suggestions; load it when you first self-review a diff (Phase 5, or a Trivial change).
7. **A feature is not done until it is documented.** Phase 6 produces documentation inside the repo; verification checks it like any other requirement.

## Adaptive depth

Scale the ceremony to the work. Before starting, classify:

- **Trivial** (nothing observable changes for a user of the code and there is nothing a requirement could be written about — typo, rename, comment, formatting, version bump): skip SDD entirely; just do it. If you could state the change as an `R#` with a Given/When/Then, it is at least Small — a collapsed `spec.md` is cheap, and a wrong Trivial call costs the spec, the docs, and the dead-code sweep. The junk-code checklist and the project's existing quality tooling still apply — run each gate once before you change anything and treat only new failures against that run as blocking (there is no plan to record a baseline in). A gate that cannot execute at all — missing service, dependency, or config; a run that collects nothing — is not a passed gate: say so explicitly, and if the change's correctness depends on it, treat the work as Small.
- **Small** (one capability, < ~1 day): collapse to a single `spec.md` — keep the template's header block (Status, Owner, Last updated) plus Objective, Requirements, Non-goals (a single line is fine), Edge cases, and Decisions, and end it with a `## Tasks` section in the tasks format, omitting the **Component** field (there is no plan; tasks reference `R#`/`E#` directly). Phases 0, 3, and 4 are skipped; specify, clarify, implement, document, and verify still run. Run Phase 3's tooling-discovery step (including its proposal of a minimal setup when a gate has no tooling) and record the gate commands, their baselines, the **Base** line — base branch @ SHA — and the **Integration** line next to the tasks (baseline = one run of each gate on the untouched tree, and **Base** as in Phase 3; Phase 5 confirms the **Base** line before the feature's first commit). Wherever the workflow or a reference says `plan.md` or `tasks.md`, use the corresponding sections of the collapsed `spec.md` — gates and tasks next to `## Tasks`, verification gaps and reports appended there too. Documentation may be a README/doc-comment update instead of a full doc page.
- **Standard** (one feature, multiple components): full workflow, phases 1–7. Decomposing into independently testable pieces is normal here and is not a reason to split — a piece that is worthless on its own (a restore with nothing to restore from) belongs to this feature.
- **Large** (bundles capabilities that are each shippable and valuable on their own, not merely testable on their own): run Phase 0 first and split into one spec per capability.

If work at any depth reveals a larger scope than classified, stop and re-classify: enter the workflow at Phase 1 and treat the diff written so far as input to the spec, not approved work — propose keeping or reverting it when the spec is approved. Whatever is kept is this feature's work, so Phase 3's gate baselines are still measured with that diff removed. Cost overrun is a different signal with a different response: when the work has visibly outgrown the size its depth states — a Small feature still running days later, a task that has taken several sessions instead of one — the scope has not changed, so do not re-classify; stop and report what is done, what remains, and that the depth's stated size no longer holds, then let the user choose to cut scope (Phase 7's **deferred** verdict), continue, or re-scope. Adding a heavier depth's ceremony to a feature already in flight helps nobody.

State the chosen depth in one line before starting — for Trivial, that line ("treating this as Trivial — no spec") is the user's chance to object. When unsure, ask which depth they want instead — one sentence, not a questionnaire. The user may also direct a lighter depth than the size suggests ("skip the plan — just tasks"): note the mismatch in one line, record their choice as a Decisions entry in `spec.md` (Trivial has no spec — the stated line is the record), and apply the chosen depth's rules exactly as written — Small's collapsed `spec.md` with gates and tasks inline, not a half-run of Standard. The re-classification rule above still applies if the lighter depth proves wrong.

## Workflow

### Phase 0 — Scope check *(only for Large)*

If the request bundles multiple capabilities that could each ship and deliver value on their own, map them before writing anything:

- List each capability with a stable slug, a one-line responsibility, and its dependencies on the others.
- Propose the split and an order. Get approval.
- Write the approved split to `specs/<parent-slug>/scope.md` — a `Last updated` line plus one row per capability: slug, one-line responsibility, depends-on, **rank** (the order the user approved, by value delivered — the tiebreak when several capabilities are unblocked at once), and status (`pending` | `in-progress` | `done` | `deferred` | `abandoned`). `deferred` means cut from this release by a dated decision, not dead: the row carries that date and an owner, exactly like a deferred requirement, so a later session picks it up again — `abandoned` stays reserved for a capability that is not coming back. Each capability then gets its own sibling `specs/<capability-slug>/` directory.
- Then run Phases 1–7 per capability, respecting dependency order, and update that capability's status in `scope.md` as it lands.

### Phase 1 — Specify

Produce `specs/<slug>/spec.md` from `assets/spec-template.md`.

- Before writing, test the slug against surviving evidence: `docs/<slug>.md`, a branch named `<slug>`, `<slug>: ` commits in `git log`, or a `scope.md` row for it, with no `specs/<slug>/` on this or any other active branch (enumerated as in Phase 3's overlap scan), means this feature's artifacts were deleted — recover them under Resuming work's missing-artifact rule instead of specifying it fresh.
- Fill the header's **Owner**, **Sign-off**, and **Tracking** lines from the repo, never from assumption: who is accountable for the spec's content; which role must sign off on each approval-gated item this feature raises (spec content, sensitive-ground `R#`/`E#`, a new dependency, an irreversible data change, a delivery step against a shared, staging, or production environment); and where the team tracks open work outside the repo. Read `CODEOWNERS`, the contribution/review policy, issue and pull-request templates, security or operations docs, and the identifiers existing specs and commits cite. `— the session's user holds all of these` and `— this project tracks work in the repo only` are valid, common answers — record them explicitly. Discovery checklist in [references/team-and-review.md](references/team-and-review.md).
- Capture **what** and **why** — never *how*. No tech-stack, file names, or architecture in the spec.
- Turn every requirement into acceptance criteria (Given/When/Then or checkable statements), and close the Requirements section with a **Minimum shippable** line naming the smallest set of `R#`/`E#` that still delivers the Objective — the answer to "what do we drop?", written before anyone has to ask it; rules in [references/writing-specs.md](references/writing-specs.md).
- Name the surfaces the feature exposes (UI, API/contract, CLI, background job, data pipeline, library) and the sensitive ground it touches (authentication/authorization, personal or regulated data, secrets, money). Where the feature faces users or runs in production, also state the operational criteria it must meet (load and volume, accessibility, text and locale, the signal that shows it working or broken, behavior when a dependency degrades, what an operation that writes in more than one place leaves behind when it fails halfway). Each one brings a class of criteria the spec must cover with `R#`/`E#` or declare a non-goal in writing — tables and checklist in [references/writing-specs.md](references/writing-specs.md); anything you cannot answer becomes a `[NEEDS CLARIFICATION]`.
- State non-goals explicitly: what this feature deliberately does not do.
- Define measurable **success criteria** with stable `SC#` ids — real-world checks beyond tests passing (a metric, a manual script, a rollout gate); each names the signal it reads (metric, log, dashboard, report) and where it is read — and where this feature must produce that signal, emitting it becomes a plan component and a task, never an assumption that something already emits it. Phase 7 walks and reports them by id. The collapsed Small spec omits them.
- Mark anything you had to assume with `[NEEDS CLARIFICATION: question]` inline.
- For writing quality — testable criteria, anti-patterns to avoid — see [references/writing-specs.md](references/writing-specs.md).

### Phase 2 — Clarify

Before planning, resolve every `[NEEDS CLARIFICATION]` marker:

- Ask the user the open questions, batched, most-consequential first.
- Fold the answers back into `spec.md` and delete the markers.
- If the user says "you decide", record the decision *and its rationale* in the spec's Decisions section.

Exit criteria: zero markers left, and the spec approved by everyone its **Sign-off** line names. Where a named signer is not in this session, the spec still exits on the user's approval but carries `pending sign-off: <role>` on its Status line until that signer answers — and no work the pending item gates starts meanwhile (core rule 2).

### Phase 3 — Plan

Produce `specs/<slug>/plan.md` from `assets/plan-template.md`.

- Read the actual codebase first — the plan must reference real files, real modules, and the project's existing conventions, not a greenfield fantasy. Also scan every `specs/*/` in the repo — in a monorepo that means each package's `specs/`, not just this one's — for other in-flight features (Status `in-review` or `approved`) whose plan claims files or symbols this plan touches. A feature developed on its own branch has no artifacts in this tree, so also read the specs on the other active branches — those holding commits not yet merged here and touched in the last ~90 days (`git for-each-ref --sort=-committerdate --format='%(refname:short) %(committerdate:short)' --no-merged HEAD refs/heads refs/remotes`); list each one's specs with `git ls-tree -r --name-only <branch> | grep -E '(^|/)specs/'` and read them with `git show <branch>:<path>`. Where branches cannot be enumerated, ask the user which other features are in flight. Record the branch set you scanned — or the user's answer — in the plan's Current state; an empty scan means "none", never "not visible". Surface any overlap to the user before asking for approval.
- Discover the project's quality tooling (linter, formatter, type checker, test runner, plus any other check the project already runs in CI or its scripts — accessibility, security or dependency scan, size or performance budget, contract/schema check) and record the exact commands (in a monorepo, scoped to the package that owns the code, so sibling features' failures stay out of the run) in the plan's Quality gates section — these become mandatory checks for every task. Every recorded command must be read-only — it reports, it never rewrites the tree: record a writing tool's check form (`cargo fmt --check`, `mix format --check-formatted`, `black --check`, `prettier -c`), never its default (`cargo fmt`, `mix format`, `black .`); a formatter gate that always exits 0 is not a gate. Run each command once on the untouched tree — a tree holding none of this feature's work; where a diff already exists (re-classified work), stash it and measure without it, or measure at the ref this feature will start from — and record as that gate's baseline what the run shows: its pre-existing failures (enumerated, or a total where the backlog is too large to list) and, for the test gate, its skipped count — gates are judged as *no new failures*, not absolute zero. Record the base branch this feature starts from and the commit that run measured on as the plan's **Base** line (a branch name that still resolves later, never a bare SHA or `HEAD`, plus `git rev-parse HEAD` on that untouched tree — later passes test `git merge-base HEAD <that branch>` against the SHA to detect a rebase or a merged-in base); Phase 5 confirms it before the feature's first commit. A gate that does not reproduce its own result is nondeterministic: a failure a re-run on the untouched tree does not reproduce belongs in the baseline too, marked `flaky`. Each gate also records **where it runs**: `here`, or `pipeline-only` when the project enforces it automatically on every change but it cannot execute in this environment because its credentials or infrastructure live in the pipeline. A pipeline-only gate is a recorded gate — not missing tooling and not the non-executable case below: it has no local baseline, and Phase 7 evidences it from that pipeline's run on this change set ([references/verification.md](references/verification.md)). A command that cannot execute at all — missing service, dependency, or config, e.g. a test run that collects nothing because a database is unreachable — has no baseline and must never be recorded as one: stop and ask the user to make it runnable, or record their refusal as a Decisions entry in `spec.md` so Phase 7's manual-verification exception applies. A gate lacks tooling only when nothing in the project can perform its check — in *statically typed* compiled languages the build command is the type gate (`go build ./...`, `cargo check`), but where the language compiles without type-checking (Elixir, Erlang, Clojure) the build is no type gate: record the project's configured analyzer (`mix dialyzer`) instead, and treat the gate as genuinely missing when none is configured. Where a gate is genuinely missing, say so there and propose a task adding a minimal setup; never adopt heavy tooling uninvited — and a check this project never ran is not a missing gate: proposing one is its own spec discussion, not a Phase 3 step. If the user declines the setup, record the refusal as a Decisions entry in `spec.md` — Phase 7's manual-verification exception depends on it.
- Record how this change set reaches its base branch as the plan's **Integration** line, next to **Base**: read the project's own policy — `CODEOWNERS`, branch-protection or required-check configuration, the contribution/review policy, a pull-request template — and state whether the feature lands as direct commits or as one or more review-gated change sets, who must approve each, and which checks are required there (they usually overlap the `pipeline-only` gates above — say which). `— direct commits to the base branch, no review policy found` is a valid answer: record what the repo shows and never propose a review process the project does not have. Pushing, opening, or merging a change set acts on shared ground and is the user's step, like a delivery step; Phase 7 checks the resulting integration state before the terminal status — rules in [references/team-and-review.md](references/team-and-review.md).
- Every requirement stating a number (latency, memory, payload size, query count, throughput) gets the command that **measures** it recorded next to the gates in the plan, together with the value the untouched tree shows today where the behavior already exists and the conditions that value was measured under (environment, data scale, concurrency, run count). Discover the project's benchmark/profiling tooling the same way as the gates; where nothing in the project can measure it — or nothing here can reproduce the conditions the number actually means, so the command measures a different question (toy data, a single run, a laptop for a production p95) — the missing-gate rule above applies: propose a minimal setup, or record the user's refusal and move the criterion to an `SC#` naming its measurement method and the environment it is measured in ([references/writing-specs.md](references/writing-specs.md)).
- Map the architecture before proposing components: how the repo organizes code (layers, feature folders, modules, hexagonal — whatever the tree actually shows) and where each kind of thing lives; record it in the plan's Current state. Where no coherent pattern exists, say so there and follow the dominant local convention of the area being touched — never introduce a new architecture as a side effect of a feature; proposing one is its own spec.
- Search for reusable code before planning any new code: existing helpers, services, and shared modules that already do — or nearly do — what a component needs (search by behavior, not just name: grep for the domain terms, read the shared/core/util areas, check what similar existing features call). Each component's **Reuses** line names what it extends or calls, or states what was searched and why nothing fit. New code is the fallback, not the default — prefer extending an existing module (within its responsibility) over creating a parallel one. Reuse-first covers third parties too: when nothing internal fits and the component needs code the project does not have, read the manifest before reaching outside — a dependency the project already declares and that nearly fits is extended like internal code, and anything genuinely new is recorded on the plan's **Dependencies** line below, never introduced as a task's side effect.
- Identify components to build/change, dependency order between them, risks with mitigations, and what can proceed in parallel. Place every component where the mapped architecture says that kind of thing lives; a component that breaks the pattern needs a stated reason in the plan.
- Record three lines in the plan: **Data changes** — whether any component alters the shape of stored data or values already stored, and for each change the target datastore its commands run against plus the check that proves the data survived — **Delivery** — whether the feature needs anything beyond the project's normal release to reach users (a flag, config, ordered rollout, manual step) — and **Dependencies** — whether the feature adds a third-party dependency, changes the version of one already present, retires one, or calls an external service at runtime. `— none`, `— ships with the normal release`, and `— none` are valid answers; anything else follows the checklists in [references/data-and-delivery.md](references/data-and-delivery.md) and [references/dependencies.md](references/dependencies.md), which also decide the migration task's verification, who retires a flag, who executes each delivery step and against which environment, the stages an ordered rollout advances and rolls back through, how a new config value or secret reaches each environment, and — per dependency — how it enters (manifest plus committed lockfile, vendored copy, private mirror) at an exact pinned version, its license, its maintenance and open advisories, its weight and install-time behavior, the cost and limits of a metered service, the provider contract version the integration targets and what stands in for it in tests, the blast radius of a version change on that dependency's other callers, and who removes one this feature retires. Adding a dependency, or changing the version of one other code shares, is presented for the user's explicit sign-off before approval (core rule 2) and is never a side effect of a task; a version change no `R#`/`E#` of this spec needs is its own spec discussion, like a new architecture. Discover the project's migration mechanism, pipeline, environments, flag system, manifest, and lockfile by reading the repo; record what exists, propose nothing uninvited. At Small, record all three lines next to the tasks in the collapsed `spec.md`.
- Every requirement and edge case (`R#`, `E#`) in the spec must map to at least one component in the plan. If something in the plan implements nothing from the spec, cut it.
- Stop and get approval.

### Phase 4 — Tasks

Produce `specs/<slug>/tasks.md` from `assets/tasks-template.md`.

- Each task is completable in one focused session, names the files it touches, and carries its own acceptance criteria and a concrete verification step (a command to run, a test that must pass — or, where the project has no runnable test runner and the user declined the setup proposed in Phase 3, a manual check the user approved).
- Order by dependency; mark tasks that can run in parallel with `[P]`.
- Every plan component must be covered by at least one task.
- Include a documentation task (Phase 6's work) so it is scheduled, not an afterthought.
- Stop and get approval. Present the magnitude with the list, in one line and in the depth's own unit: how many tasks, which of them are the large ones (judged against how comparable work has gone in this project, never an invented estimate), and the size the chosen depth states — so the approver can object to the commitment before approving it instead of after.

### Phase 5 — Implement

Execute `tasks.md` in order:

- If the repo uses git, do the feature's work on a branch named for the slug — or prefix its commits with `<slug>: ` — so Phase 7 can reconstruct the feature's change set in a later session. Before the feature's first commit, confirm the plan's **Base** line under Quality gates — the branch point when the feature has its own branch, the tip of the shared branch at that moment when its commits are slug-prefixed; Phase 7 and any re-baseline read it from there instead of guessing `main`. Commit as tasks land where the user allows commits; if work stays uncommitted, leave the working tree intact so Phase 7 can still see it. Uncommitted work is invisible to every other session and every other clone, so it is never a handoff state: before handing the feature over or leaving it, commit it or record it in the task's note as `uncommitted, local to <who>`.
- One task at a time, and only a task nobody else holds: before starting, confirm its **Owner** is `—` here and — where the feature's work spans branches — in the same slug's `tasks.md` on the other active branches (enumerated as in Phase 3's overlap scan); then claim it by setting **Owner** to who (or which branch) is executing it plus today's date, and commit that claim before writing code. Release it (**Owner** back to `—`) on completion or handback. A claim older than the project's normal task span is stale, not held — ask the user before taking it. Load only the spec/plan sections relevant to the current task, not everything.
- Write or update tests that encode the task's acceptance criteria — tests are the executable form of the spec. Where the project has no runnable test runner and the user declined the setup proposed in Phase 3, the task's `Verify:` is instead a user-approved manual check, cited with its observed output — exception in [references/verification.md](references/verification.md) step 2.
- Write code that reads like the surrounding codebase: same conventions, same naming, same structure. New abstractions need a current — not hypothetical — second use.
- Before marking a task done, pass the gates: run the task's verification step **and** every quality gate recorded in the plan (tests, lint, format, types, and every other gate recorded there) with no new failures against its baseline, then self-review the diff against the junk-code checklist in [references/clean-code.md](references/clean-code.md).
- Update the task's checkbox and add a one-line completion note in `tasks.md` as you go.
- If implementation reveals the spec or plan is wrong, **stop** — go back to the affected phase, amend the artifact with the user (a standing waiver does not cover this), then resume. Do not improvise around the spec.
- **A deliberate shortcut is declared, never silent.** Where a task ships code that meets its `R#` but knowingly does not do what the plan's component describes — a narrower correctness than intended, a duplication left in place, a step skipped for time — the spec is not wrong and the gates will not catch it, so the record is the only thing that will: add a dated Decisions entry in `spec.md` naming what was traded, what the proper version is, and who owns it (an open follow-through — [references/team-and-review.md](references/team-and-review.md)), cite that entry in the task's completion note, and let Phase 7 report it.

### Phase 6 — Document

Documentation lives in the repo and ships with the feature:

- Produce `docs/<slug>.md` from `assets/doc-template.md`: what the feature does, how to use it, its public API/interface, and a link back to `specs/<slug>/` for the full history. Where the plan's **Delivery** is not `— ships with the normal release`, the spec carries an operational-signal `R#`/`E#`, or the plan's **Dependencies** line records an external service the feature calls at runtime, the page also carries the template's **Operating** section — the switch that controls the feature and how to turn it off, the signal that shows it working or broken and where it is read, what a human does when that signal fires, and, for a runtime external service, that service, the provider contract version the integration targets, and where its status or incidents are read; remove that section otherwise.
- Update the project's existing entry points: README (if the feature is user-facing), CHANGELOG (if the project keeps one), and doc comments on the public interfaces the feature exposes.
- Follow the project's existing documentation conventions if it has any (`docs/` layout, docstring style, ADRs); create the `docs/` folder only if nothing exists yet. Where a Decisions entry binds beyond this feature — an architecture pattern, a dependency other code will share, a cross-cutting convention, a targeted contract version — and the project keeps its own decision record (discovered by reading the repo: `docs/adr/`, `decisions/`, an RFC folder), write that entry there too in the project's existing format and link it both ways with the spec's Decisions line; where the project keeps none, say so in one line and never start the practice uninvited.
- Documentation describes behavior as specified — if writing it exposes a mismatch with the code, that is spec drift: handle it in Phase 7, don't paper over it.

### Phase 7 — Verify

When every task is done, waived, or deferred, run a convergence pass — full procedure in [references/verification.md](references/verification.md):

- Give every requirement and edge case (`R#`, `E#`) a verdict — **met / partially met / not met / spec drift / superseded / deferred** — citing real code and the passing test as evidence. Then run the quality gates over the whole change set, sweep it for junk code, and check the documentation matches actual behavior.
- Anything the feature added that nothing reaches gets a **deletion gap task** — deletion is the default; the inventory procedure and the keep exceptions are in [references/verification.md](references/verification.md).
- Report the verdict table, append gaps to `tasks.md` as `G#` tasks, and get approval before implementing them (a standing waiver recorded under core rule 2 covers this approval too — gaps are still reported, just not blocked on; deletion gaps are the exception and always need explicit confirmation before anything is deleted). Append the dated report block to `tasks.md` so its evidence, manual-verification citations, and pending `SC#` checks survive the session — format and append rules in the same reference. Repeat the pass until every requirement and edge case (`R#`, `E#`) is *met* (or *superseded*, or *deferred* by a dated decision on record, or an unreachable one the user accepted as a documented limitation), the gates pass with no new failures against the baseline recorded in the plan, and the docs are accurate.
- On completion, confirm the change set's integration state against the plan's **Integration** line: either it is merged into the branch the plan's **Base** names (`git merge-base --is-ancestor HEAD <that branch>`) with the approvals that line requires on record, or the pass reports `Integration: pending review (<identifier>)` on its report block and the Status stays **approved** — pending blocks the terminal status, never the report, the same shape as a pipeline-only gate. Any edit to the change set after a converged pass — review fixes included — invalidates that pass's report: run Phase 7 again first. Once it is merged, set the Status of `spec.md` and `plan.md` to **implemented** — which means this change set is merged and verified *in the repo*, never that the feature is live: where the plan's **Delivery** records rollout stages the feature has not finished, state that on the spec's Status line (`implemented — rollout in progress, stage <the one it is at>`) with a dated owner for the final stage, the same way an introduced flag carries a retirement owner, and reduce it to plain **implemented** when the last stage completes; `tasks.md` stays `approved` — its checkboxes, completion notes, and appended reports are its completion record (at Small there is one artifact: the collapsed `spec.md` takes the spec's status and becomes **implemented**, its `## Tasks` section being that completion record). If a later feature replaces this one, mark the old spec and its plan **superseded** (linking to the successor) and the doc page **deprecated** — never delete the history.

## Change requests mid-flight

When new or different behavior is asked for after the spec is approved — by the user, or by a code reviewer or any third party whose feedback the user relays — the change enters through the spec, not the code:

- Amend `spec.md` first (new/changed `R#`/`E#`, a Decisions entry recording what changed and why), then update `plan.md` and `tasks.md` if the change touches them, then implement.
- Behavior feedback from a code review is a change request like any other, whoever relays it: it lands in `spec.md` first — new or changed `R#`/`E#`, plus a Decisions entry naming the reviewer and the review identifier — never straight in the diff, or Phase 7 reports the reviewer's own decision as spec drift. A comment that changes nothing the spec states (naming, structure, style) is ordinary Phase 5 work, and a reviewer's rejection of a plan choice goes back to Phase 3, not into the code. What counts as behavior feedback, and how the review identifier is recorded, is in [references/team-and-review.md](references/team-and-review.md).
- For a Large split, if the change adds a capability, removes one, or moves behavior between capabilities, update `specs/<parent-slug>/scope.md` first (add or adjust the capability row, its depends-on, and its status) with the user's approval — then amend the affected capability's `spec.md` as usual.
- A clarification that changes no requirement → just a Decisions entry.
- If the change invalidates completed tasks, list which ones and get approval before redoing them.
- Amending a spec whose Status is already **implemented** resets it (and `plan.md`) to `in-review`; it then re-walks the normal lifecycle — `approved` on the user's sign-off of the amendment, `implemented` again once the new `R#`/`E#` pass Phase 7. If the change replaces the feature's behavior wholesale, write a new spec and mark the old one **superseded** instead of reopening it. If it replaces only part of what *another* feature's spec still claims, amend that spec in the same approval — a Decisions entry, plus `— superseded by specs/<successor-slug>/spec.md` on each affected `R#`/`E#`; supersede the whole artifact only when nothing in it stays live. That annotation is records-only: it does not reset an **implemented** spec's Status — only adding or changing a live `R#`/`E#` does — and Phase 7 reports each annotated requirement as **superseded** instead of re-verifying it.
- **If the user cancels the feature at any phase**: set its artifacts' Status to **abandoned** with a Decisions entry saying why — never delete the directory. Then propose reverting whatever change set already landed (built the same way as the step-6 inventory in [references/verification.md](references/verification.md)) unless the user explicitly keeps parts; record what was kept or reverted in that same Decisions entry, and mark any existing `docs/<slug>.md` **deprecated**. Every reverted task's `- [x] Done` goes back to `- [ ] Done` with a note naming the revert, so task state never claims code the tree no longer has. If the feature is a capability of a Large split, set its `scope.md` row to **abandoned** and, in the same approval, resolve every capability that depends on it — re-point, absorb, or abandon it too.

The one-line test: if the diff you are about to write isn't covered by the current spec, stop and amend the spec first.

## Resuming work

When picking up an existing feature: if the user named none, resume the one matching the current branch or the most recent `<slug>: ` commits; otherwise read only the header block of each `specs/*/spec.md`, list the features whose Status is `in-review` or `approved`, plus any **implemented** one whose Status line records a rollout still in progress, whose Decisions hold an open dated follow-up (a flag retirement, a cleanup step, a provider end-of-support move, a pending `SC#`, a requirement deferred out of the change set, the proper version of a declared shortcut), or whose `tasks.md` holds a `- [>] Deferred` entry — those stages and follow-ups are open work (skipping `implemented` with none of those, `superseded`, and `abandoned`; a directory holding `scope.md` and no `spec.md` is a Large parent — see that bullet below), and ask which one. Then read its artifacts (`spec.md` → `plan.md` → `tasks.md`) — if `specs/<slug>/` is absent here, the feature is most likely developed on its own branch: find and read its artifacts there as in Phase 3's overlap scan (`git ls-tree`/`git show`), and switch to that branch to resume the work rather than continuing from this one. Find the first unchecked task no one else holds (its **Owner** is `—` — Phase 5's claim rule) — a task marked `- [~] Waived` is closed, and `- [>] Deferred` is not due until its date — and confirm with the user before continuing.

- **Work-present check** — before anything else, confirm each checked task's work is actually in *this* tree: its **Files** exist and its `Verify:` passes. A checked task whose work is absent here was never handed over — recover it from the branch or clone the task's note names, or reopen it (`- [x] Done` → `- [ ] Done`, with a note saying where it was last seen). Never trust the checkbox alone, and never file a `G#` to re-implement work a teammate already did before this check has run ([references/team-and-review.md](references/team-and-review.md) → Handoff).

- **Drift check** — to tell whether code changed *outside* this feature since the artifacts were written, compare each artifact's `Last updated` date against `git log` for the paths the feature touches, discounting the feature's own work — commits on its branch, commits carrying the slug prefix, and the working tree its last completed task left behind are never drift; if anything else is newer, run Phase 7 first as a diagnostic pass to detect drift. Dates also mislead after a rebase or a merge from the base branch: if `git merge-base HEAD <the branch named in the plan's **Base** line>` no longer equals the recorded **Base** SHA, the branch was rebased or the base merged in — treat the code as changed regardless of dates and run that pass, whose step 4 refreshes the stale baseline.
- **Artifact cross-check** — every spec `R#`/`E#` carries at least one task (for Small, in the collapsed `spec.md`'s `## Tasks` section) and, at Standard and Large, appears in the plan's Requirement coverage table; in reverse, no coverage row and no task's `Implements` may name an `R#`/`E#` the spec no longer has. Then check each artifact against its own history, discounting the workflow's own edits the same way — task checkboxes and completion notes, amendments, Status changes, appended verification reports, and `Last updated` bumps are legitimate in an `approved`/`implemented` artifact, whether committed on the feature's branch or under its `<slug>: ` prefix or still uncommitted from its last completed task, and are never mismatches. What counts is an edit outside that set: a commit touching the artifact that is newer than its `Last updated` line (`git log -1 --format=%as -- <artifact>` — author date, which a rebase preserves where committer dates do not) and is neither on the feature's branch nor `<slug>: `-prefixed, or an uncommitted change (`git diff -- <artifact>`) that rewrites an `R#`/`E#`, its acceptance criteria, or the plan's components. Any such mismatch means the spec was hand-edited — treat it as an unprocessed change request and run the Change requests mid-flight procedure above before continuing. An artifact the depth never produces (no `plan.md` at Small) is never a mismatch; one the depth should have produced but that is absent is the next bullet's case.
- **Missing or unrecoverable artifacts** — rule out the branch case first: if a branch named `<slug>` or another active branch (enumerated as in Phase 3's overlap scan) holds `specs/<slug>/`, nothing was lost — the feature's work lives there; switch to that branch to resume it, or ask the user, and never restore copies into the current branch. Otherwise, if an artifact the lifecycle already produced (its upstream artifact is `approved` or `implemented`, or a downstream artifact references it) is missing or unreadable, restore it from git history; if it is unrecoverable, regenerate it from the surviving artifacts (`tasks.md` from the plan's components), leave every regenerated task unchecked, record the reconstruction as a Decisions entry in `spec.md`, get the regenerated artifact re-approved, then run Phase 7 immediately as a diagnostic pass — its **met** verdicts, not memory of earlier sessions, decide which regenerated tasks are already done.
- **Stopped at an earlier phase** — a feature whose artifacts simply stop at an earlier phase resumes at that phase's exit instead: an `in-review` artifact is re-presented for approval, not treated as lost.
- **Every task closed, Status still `approved`** — read the `Verification reports` section of `tasks.md` (for Small, the end of the collapsed `spec.md`'s `## Tasks` section). No report block, or a last pass still listing open gaps or verdicts other than **met**/**superseded**/**deferred**/an accepted limitation, means Phase 7 never converged — run it, and never set a Status to **implemented** without a converged report block on record.
- **Large split** — read `specs/<parent-slug>/scope.md` first and pick the next capability whose dependencies are `done`; where several qualify, take the one the approved **rank** names first and report that choice rather than picking silently — a different order is a re-rank of those rows with the user's approval, never a silent divergence. A `deferred` row is not a candidate until its date, and is reported alongside the in-flight rows so a cut capability stays visible. If none qualifies, report the blocking rows to the user instead of stopping — an `abandoned` dependency is a scope decision to make (re-point, absorb, or abandon the dependent), never a permanent block.
- **Abandoned** — skip features whose artifacts are `abandoned` unless the user explicitly reopens them; reopening sets `spec.md`, `plan.md`, and `tasks.md` back to `in-review`, and the normal lifecycle re-applies from there. After re-approval, run Phase 7 immediately as a diagnostic pass — its **met** verdicts, not checkboxes left behind before the cancellation, decide which tasks are still done and where Phase 5 restarts.
