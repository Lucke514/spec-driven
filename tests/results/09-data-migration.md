## Friction log

### F1 (D2, D8, D10 — severe, the headline finding) — Phase 7's entry condition has no path forward for a required task only the user can execute
**Where** — SKILL.md → Workflow: *"7 — Verify… When every task is done, waived, or deferred, run a convergence pass."* Cross-cutting with `references/data-and-delivery.md` → Target: *"A command whose target is shared, staging, or production is a stop-and-ask — never a command the agent runs on its own."*
**What went wrong** — T4 ("Run the migration and backfill in production") is required (it's inside the spec's Minimum shippable line), in scope, and cannot honestly become `- [x] Done` (the agent has no production access), `- [~] Waived` (nothing is being declined), or `- [>] Deferred` (deferral means "not in this change set," and R2/SC2 *are* in this change set). All three task-template box states are wrong for this task's actual state. Because Phase 7's entry condition is literally "every task is done, waived, or deferred," **the feature can never legitimately reach Phase 7 at all** — not "reaches it with caveats," but has no rule-sanctioned door into it. The only way I found to produce anything was borrowing `references/verification.md` → Handling gaps → Diagnostic passes, whose own stated triggers are "a resume drift check, regenerated artifacts, a reopened feature" — none of which describes a first pass blocked on a stop-and-ask. This is not a corner case: it is the *normal* shape of a real production data migration (schema change + backfill are almost always human-gated production steps), and the scenario's own prompt already flagged this as an open wave-A finding — it is still open in v3.0.0.
**Why** — the task box-state vocabulary (`Done`/`Waived`/`Deferred`) and the Phase 7 entry gate were both designed around "the agent can eventually finish everything or explicitly choose not to," with no state for "correctly gated behind a human step that is neither declined nor pushed to later, just not yet done." The convergence-loop escape hatch (`references/verification.md` → Convergence loop: *"stop the loop and put the choice to the user (accept it as a documented limitation, defer it with a date and an owner, change the spec, or add the missing tooling)"*) offers exactly four outs, and none of them is "the user will run this for real later and then it becomes genuinely met" — the single most common real-world resolution for this class of feature.
**Fix shape** — add a fifth task box state (e.g. `- [!] Pending execution — YYYY-MM-DD, blocked on <who/what>`) that is neither open, waived, nor deferred, and let Phase 7's entry condition read "done, waived, deferred, or pending execution on a recorded stop-and-ask" — with the terminal `implemented` status still correctly blocked until it clears (the same pattern Integration's `pending review` already uses to not block the report but block the terminal status). Add "pending execution" as a fifth convergence-loop escape-hatch option, or fold it into the same case as `blocked (pre-existing)`/`blocked (flaky)` in the verdict table, since it shares their shape: reported, not gapped, doesn't block exit, but also isn't `met`.

### F2 (D10 — moderate) — no verdict fits "implementation complete and tested against a stand-in, real execution pending"
**Where** — `references/verification.md` → Procedure step 3's verdict table (`met` / `partially met` / `not met` / `blocked (pre-existing)` / `blocked (flaky)` / `spec drift` / `superseded` / `deferred`).
**What went wrong** — R1's migration SQL and R2's backfill script are both fully written, code-reviewed, and (for R2) exercised with passing tests plus a negative control against the in-memory stand-in — by any normal engineering measure, "done." But `references/verification.md` → Stored-data requirements requires the *actual production run's observed output* as R1/R2's evidence, which does not exist. `partially met`'s own definition ("missing edge case, missing test, an assertion that cannot observe the criterion") does not describe this state at all — nothing is missing from the test suite; what's missing is a real database. I used `partially met` anyway as the least-wrong label and said so explicitly on the report, but a reviewer skimming the verdict table alone would misread "partially met" as "the code isn't finished," which is false.
**Why** — the verdict table's categories are all about the *code's* completeness or a *gate's* attribution; none addresses "the code is correct and tested against every stand-in available, and the remaining gap is a real-world execution this session structurally cannot produce."
**Fix shape** — a `blocked (pending execution)` verdict, parallel to the existing `blocked (pre-existing)`/`blocked (flaky)`, sharing their "reported, not gapped, does not block exit" shape but reserved for stored-data/delivery requirements whose only outstanding evidence is a stop-and-ask the user has not yet performed.

### F3 (D3, D2 — moderate) — the Owner claim-and-commit dance leaves no artifact trace by design, so nothing catches its omission
**Where** — SKILL.md → Phase 5: *"claim it by setting Owner to who… plus today's date, and commit that claim before writing code — one commit, always, whatever the scan found."*
**What went wrong** — in this run, every task went from `Owner: —` directly to `- [x] Done` with no separate claim commit ever made. Nothing in the artifact itself (the final `tasks.md`) reveals this happened, because the terminal state — `Owner: —`, released on completion — looks byte-for-byte identical whether the claim-commit rule was followed and then correctly released, or skipped outright. This is a real omission on my part (not a fixture-forced one — this repo has git and nothing prevented a claim commit), but it's also a rule whose violation is close to unfalsifiable after the fact from the file alone.
**Why** — the claim's only observable trace is a *commit that existed and then was superseded* — `git log` on the branch, not the current file content. A reader (or a future Phase 7 pass, or this very audit) checking artifact fidelity from `tasks.md` state alone cannot tell claimed-then-released from never-claimed.
**Fix shape** — either require the claim commit's SHA to be cited in the task's completion **Notes** line (so the trace survives in the artifact that everything else already reads), or accept that this rule is enforced only by author discipline and say so, rather than implying (as "one commit, always" does) that it is a checkable invariant.

### F4 (D8, D2 — moderate) — writing straight to `Status: approved` leaves the same kind of invisible-stop gap as F3
**Where** — SKILL.md → Core rule 2: *"No artifact carries approved without having existed as in-review first: the stop leaves a trace, or it did not happen."*
**What went wrong** — `plan.md` and `tasks.md` were both written directly with `Status: approved`, never committed in an `in-review` state first. Exactly as with F3, the final file is indistinguishable from one where the stop genuinely happened and was then approved in the same breath (a legitimate fast turnaround) versus one where the intermediate state was simply never produced.
**Why** — same root cause as F3: the rule names a *process* invariant (the stop happened) but the only artifact it leaves behind is a value on a `Status:` line, which by definition looks the same regardless of whether the process step actually ran. Git history is the only real witness, and nothing in the workflow requires citing it.
**Fix shape** — same as F3: have the phase's exit action (or the completion note / a Decisions entry) name the commit or timestamp at which `in-review` was set, so "the stop leaves a trace" is checkable from the artifact plus one `git log`, not just asserted.

### F5 (D6, D2 — moderate) — the Stored-data Target checklist has no answer for "no rehearsal environment exists at all"
**Where** — `references/data-and-delivery.md` → Stored-data checklist → Target: *"the datastore each data-change command runs against… (a disposable local instance, an ephemeral CI database, a restorable copy). A command whose target is shared, staging, or production is a stop-and-ask."*
**What went wrong** — this fixture (like S02's before it) has *no* disposable local instance, no CI database, and no restorable copy — `pg` is a declared dependency that is not installed, and there is no network. The Target bullet's three named forms are all "a real Postgres I could safely run this against," and none of them exists here at all — a state the bullet doesn't name. I resolved this by analogy to `references/verification.md` → Recording gates' "a command that cannot execute at all… has no baseline and is never recorded as one: ask the user to make it runnable, or record their refusal" — a rule written for the plan's Quality gates table, not for a data-change Target. The analogy is defensible but is nowhere stated for this section; a literal reading of the Target bullet alone gives no instruction for "none of the three kinds of target exist."
**Why** — the checklist implicitly assumes at least a disposable/CI environment is always available to rehearse the forward/reversal cycle Phase 5's `T#` Verify instruction requires (data-and-delivery.md: *"runs the change forward, then its reversal with rows present, then forward again"*) — this project (and plausibly many real ones, especially in a sandboxed agent session) has none.
**Fix shape** — add a fourth Target case alongside the three named ones: "no environment of any kind is reachable here — say so, propose the smallest one that would let this be rehearsed, and if that's declined or impossible, evidence the change through code review only, flagged as never having been run against real data" (which is effectively what I ended up doing, unprompted).

### F6 (D3 — minor) — core rule 2's Sign-off table doesn't list the Target/Who-executes-it stop-and-ask as its own row
**Where** — SKILL.md → Core rule 2's "Always needs explicit sign-off" table (two relevant rows: irreversible/data-losing execution, and "a delivery step… against a shared, staging, or production environment") vs. `references/data-and-delivery.md` → Stored-data checklist → Target, which independently states its own stop-and-ask for a data-change command against shared/staging/production.
**What went wrong** — running this feature's migration/backfill against production is unambiguously a stop-and-ask by the Target bullet, but core rule 2's table — which calls itself "the one list" for what the Sign-off line carries — has no row literally naming "run a data-change command against production" (only "irreversible/data-losing execution" and "a *delivery* step"). I resolved the ambiguity by treating the production execution as the "delivery step" row (their recorded forms match: "the user's go-ahead per step… with the result on the report's `Data & delivery:` line" in both places), but this required inference, not a direct citation.
**Why** — "the one list" claim in core rule 2 is contradicted by a second, independently-worded stop-and-ask elsewhere that isn't cross-referenced into it, for exactly the scenario (production data-change execution) this reference file is supposed to own.
**Fix shape** — either fold the Target/Who-executes-it stop-and-asks explicitly into core rule 2's table with their own row (even if it's simply "= the delivery-step row, restated"), or have data-and-delivery.md say plainly "this is the same stop-and-ask as core rule 2's delivery-step row, not a new one" so a reader doesn't have to infer the mapping.

### F7 (D9 — minor) — the Delivery checklist's vocabulary is visibly tuned for flag-gated app rollouts, not a one-time data change
**Where** — `references/data-and-delivery.md` → Delivery checklist ("How it reaches **users**", "How it is **turned off**", "**Flag** retirement").
**What went wrong** — none of these items are wrong to ask, but every one needed a small translation for a pure schema+backfill change: "users" became "the production database," "turned off" became "don't re-run the script, nothing to compensate," and "flag retirement" was a one-line "no flag exists." Each answer was short and correct, but the checklist reads as written for a different feature shape (a flag-gated code rollout) than the one it was just applied to.
**Why** — data-and-delivery.md bundles two genuinely different Delivery shapes — application rollouts (flags, staged traffic, revert) and one-time data-change delivery (a migration + backfill that isn't "turned off" so much as "stopped mid-run") — under one checklist without acknowledging the difference.
**Fix shape** — a one-line branch at the top of the Delivery checklist: "for a one-time data change with no code path to gate, 'turned off' means the change is simply not re-triggered, and 'flag retirement' does not apply — say so and move on," so the mismatch is named rather than silently absorbed by the person filling it in.
