## Friction log

### 1. Where: SKILL.md → Workflow table ("Status after" column: `draft` until presented, then `in-review`, then `approved`) and Phase 3/4's "Stop and get approval."

- **What went wrong**: `plan.md` and `tasks.md` were written directly to disk with `Status: approved` already set. Neither artifact was ever written in an `in-review` state, presented, and then separately flipped to `approved` in reaction to an actual user reply — the whole cycle collapsed into one file-write. This is verifiable from the run's own git history: neither file exists at any commit with `Status: in-review`.
- **Why**: Nothing in Phase 3/4's text (or the Workflow table) requires the `in-review` state to be *durably observable* before the artifact can carry `approved` — the states are named but nothing forces a session to actually pause between writing the draft and recording the approval, especially in a single continuous session under no external turn-taking pressure. Phase 1→2 has an explicit textual guard for exactly this failure mode ("never ask for approval while `[NEEDS CLARIFICATION]` markers remain" — a checkable precondition); Phase 3 and 4 have the words "stop and get approval" but no equivalent checkable precondition an agent can fail to satisfy, so there is nothing to catch a session that just... doesn't stop.
- **Fix shape**: Give Phase 3 and Phase 4 the same shape of guard Phase 1→2 has — e.g., "the artifact must exist on disk (or be shown in the transcript) in `in-review` before it can carry `approved`; a session that cannot produce that intermediate state has not actually stopped." Even a one-line procedural instruction — "write the file with `Status: in-review` first, as its own step, before recording the user's answer" — would make the skip mechanically harder to fall into.

### 2. Where: `references/verification.md` → Procedure step 2 (the R#/E# walk) vs. → Handling gaps ("report the verdict table... **Get approval, then implement**")

- **What went wrong**: While walking E2 during Phase 7, I noticed the requirement's route-level "create still succeeds" claim had never been independently tested (only inferred from two other tests). I wrote the missing test and confirmed it passed in the same breath — before reporting any verdict, before filing a `G#`, before asking the user anything. This is the exact same shape of gap run 02's own friction log flagged (S02 friction/finding on G2: "a verdict rests on... not on code-reading confidence" — here it was "not on inference from adjacent tests either), and it recurred even with that precedent on record, in a different run, working from the current version of the skill.
- **Why**: Step 2 (the walk) and "Handling gaps" (report → file → approve → implement) are two different sections, in that order, but nothing at the point of discovery — mid-walk, having just noticed a real gap — tells the agent to *stop noticing and go report* instead of fixing what's right in front of it. The natural continuation of "I see the gap" is "I know the one-line fix," and nothing interrupts that motion before it happens. Core rule 2 states the review-stop philosophy in the abstract ("stop for human review between phases") but Phase 7's gap-handling is a sub-loop the core rule's phase-boundary framing doesn't obviously reach into.
- **Fix shape**: Add a single imperative sentence at the top of step 2 or immediately after it: "A gap noticed mid-walk is reported, not fixed on the spot — finish the walk, report the verdict table, then follow Handling gaps." This is the same fix shape as #1: a checkable, explicitly-stated precondition placed at the exact point an agent's attention is on the gap, not one section later.

### 3. Where: SKILL.md Phase 0 ("Write the approved split to `specs/<parent-slug>/scope.md`...") vs. `assets/` (no `scope-template.md`)

- **What went wrong**: Every other phase artifact (`spec.md`, `plan.md`, `tasks.md`, `docs/<slug>.md`) has a matching file under `assets/` that the phase's own text names and links (`Produce specs/<slug>/spec.md from assets/spec-template.md`). Phase 0 has no such link, and no `scope-template.md` exists — the shape of `scope.md` had to be reconstructed entirely from one paragraph of prose inside SKILL.md itself, with no worked example of a filled-in header, no illustration of how a `deferred` row's date+owner should actually be written next to its other columns, and no name for what — if anything — belongs above the table (a Sign-off? an Owner? this run recorded neither, by absence rather than by an explicit "— none" the way every other artifact's header requires).
- **Why**: D3's own rubric criterion ("Templates followed; Status, Owner, Sign-off, Tracking, Last updated all filled from evidence") has nothing to check `scope.md` against, because the skill gives Phase 0 a different, thinner artifact contract than every sibling phase without saying so — an omission that is easy to miss precisely because everything else in the workflow is so consistent about pairing an artifact with a template.
- **Fix shape**: Add `assets/scope-template.md` (header: `Last updated`; the five-column table; one worked example row per status value, including a `deferred` one showing the date+owner shape) and link it from Phase 0's first bullet the same way every other phase links its template.

### 4. Where: core rule 2's table ("Adding or changing an `R#`/`E#`" — the only row that names spec-content edits) vs. `references/verification.md` → Recording gates ("record the user's refusal as a Decisions entry in `spec.md`... propose moving the criterion to an `SC#`")

- **What went wrong**: Phase 3's evidence check for R1/R2 (nodemailer can't be installed here, so real delivery can't be evidenced) led, by the reference's own instruction, to adding a brand-new `SC2` to an already-`approved` `spec.md`. Core rule 2's table is stated as "the one list" for what always needs explicit sign-off and how it's recorded — and it has a row for "Adding or changing an `R#`/`E#`," but no row for adding an `SC#`. I proceeded by analogy (a dated Decisions entry, no full re-approval cycle) because nothing else fit, but SKILL.md never actually says this is correct, and a stricter reading could argue editing an `approved` artifact outside "Change requests mid-flight" needs the same explicit re-approval an `R#` edit would.
- **Why**: The table's own framing ("that table is the list") actively discourages checking anywhere else for an approval-gated edit, so an `SC#` addition — which the skill's own reference elsewhere directs you to make — falls into a gap the table's completeness claim implies shouldn't exist.
- **Fix shape**: Either add an explicit row for "Adding or changing an `SC#`" (even if its answer is "no sign-off required, a Decisions entry suffices — unlike an `R#`/`E#`"), or add one clause to Recording gates' SC#-move instruction: "this is a Decisions entry, not an `R#`/`E#` change — no additional sign-off beyond the spec's existing Sign-off line."

### 5. Where: `references/team-and-review.md` → Integration ("Where the line records `— direct commits to the base branch`, report `direct commits — no review policy`") vs. Phase 7 step 9's three named states for the review-gated case (`merged (<id>)` / `pending review (<id>)` / `not opened yet`)

- **What went wrong**: At Phase 7, the branch was not yet merged into `main` even though the Integration policy was "direct commits, no review policy." The three named report strings in step 9 are all written for the review-gated case; the direct-commits case gets exactly one static string with no worked example of what to report when that policy also isn't merged yet. I had to synthesize "not opened yet" (borrowed from the review-gated vocabulary) as the honest answer, rather than finding it named anywhere for the direct-commits path.
- **Why**: The direct-commits case is treated as if it collapses "merged" and "not merged" into one non-question ("no review needed, so just merge it") when in fact merging is still explicitly the user's step (per the same reference's own Integration checklist), so a direct-commits feature can just as easily sit un-merged as a review-gated one — the reporting vocabulary doesn't reflect that.
- **Fix shape**: Give the direct-commits case the same three-state shape: "`direct commits — no review policy`, still report whether it is merged (`git merge-base --is-ancestor`), pending (`not opened yet`), or already landed — the policy affects *who must approve*, not *whether it happened yet*."

### 6. Where: SKILL.md Phase 0 ("update that capability's status in `scope.md` as it lands") vs. Phase 7 ("Once it is merged, set the Status of `spec.md` and `plan.md` to **implemented**")

- **What went wrong**: Phase 7 is explicit that `implemented` requires actual merge into the branch the plan's `Base` names — test-passing alone is not enough. Phase 0 never states whether a capability's `scope.md` row of `done` carries that same bar, or is satisfied by full Phase 7 convergence on the feature's own branch regardless of merge state. I treated `done` as requiring the merge (by analogy to `implemented`) since Phase 0 says "as it lands," but this is inference, not a stated rule.
- **Why**: `scope.md`'s status vocabulary (`pending`/`in-progress`/`done`/`deferred`/`abandoned`) is defined once, briefly, in Phase 0's own paragraph, with no cross-reference to Phase 7's much more carefully specified `implemented` bar — two artifacts describing what is functionally the same completion event, at two different levels of rigor.
- **Fix shape**: One sentence in Phase 0: "`done` requires the same bar Phase 7 sets for `implemented` (merged into `Base`, not merely converged on a branch) — a capability's row and its `spec.md`'s Status change together."

### 7. Where: `references/writing-specs.md` → Surfaces & their criteria (the 6-row table) applied to notification-events' actual shape

- **What went wrong**: This capability is an asynchronous side effect fired synchronously inside two existing, unmodified-in-contract API endpoints — it introduces no new endpoint, no schedule, no pipeline. None of the table's six rows (UI, API/contract, CLI, Background job/scheduled work, Data pipeline, Library/package) is a clean fit; "Background job / scheduled work" was the closest, but its own criteria (idempotency on re-run, retry/give-up) describe a re-run/retry model this capability deliberately doesn't have, forcing a Non-goal just to say the row's own criteria don't apply as written.
- **Why**: The table enumerates surfaces by *delivery mechanism* (how a human or system reaches the feature), but this feature has no delivery mechanism of its own — it rides on an existing surface's contract without changing that contract. That shape (a side effect attached to, but not part of, an existing surface's interface) has no row.
- **Fix shape**: Add a line after the table: "A feature that adds no surface of its own but rides as a side effect of an existing one (e.g., an emitted event, a triggered notification) inherits criteria from the surface it attaches to, not a row of its own — state which existing surface and which of its rules the side effect must still respect (e.g., the API contract's response-shape guarantee)."

### 8. Where: `references/clean-code.md` → Consistency ("the change reads like the surrounding codebase... Improving a project-wide convention is a spec/plan discussion, not a drive-by") vs. the same file's Leftovers bullet ("No debug output... outside real logging")

- **What went wrong**: This codebase's only prior "real logging" was bare `console.error`, used exactly once (an unhandled-rejection catch-all in `app.ts`). Adding a *second* logging channel (`console.info`, for successful deliveries, to keep them out of error-log scans) is a small but real project-convention decision — the kind Consistency's own text says belongs in a spec/plan discussion — but nothing prompted treating it as one; the leftovers bullet only asks "is this real logging or debug output," and `console.info` clears that bar easily, so the more specific Consistency concern (a *new* channel, not just *a* channel) went unexamined until self-review.
- **Why**: The two checklist bullets that jointly govern this decision (Leftovers' logging bullet, Consistency's convention bullet) sit far apart in the same document and are never cross-referenced, so satisfying the nearer, more obviously-relevant one (Leftovers) reads as satisfying the whole concern.
- **Fix shape**: Add a clause to the Leftovers logging bullet: "introducing a new logging channel or level the project doesn't already use is a convention change — flag it in the plan (Current state or Risks) rather than picking one silently during implementation."

### 9. Where: SKILL.md → Adaptive depth ("State the chosen depth in one line before starting") applied to a capability of a Large split

- **What went wrong**: I never produced a distinct "notification-events is Standard depth" statement before writing its `spec.md` — I moved directly from the approved Phase 0 split into drafting the spec, implicitly treating "a full set per capability" (the Large row's own wording) as meaning "each capability defaults to Standard," without ever saying so out loud the way the top-level Large call was said out loud.
- **Why**: The depth-statement rule reads as a top-level, once-per-feature instruction; nothing says whether a capability of an already-classified Large split needs its own restated depth line, or whether the parent classification is inherited silently. That ambiguity is exactly what let me skip it without feeling like I was skipping anything.
- **Fix shape**: One clause on Phase 0's last bullet: "each capability still states its own depth in one line before its Phase 1 begins — normally Standard, per 'a full set' above, but say so; a capability that turns out to bundle further sub-capabilities re-enters Phase 0 itself."

### 10. Where: SKILL.md → Adaptive depth, "load it when you first need it" progressive-disclosure intent (implicit across all reference links) — cost, not correctness

- **What went wrong**: Same finding as iterations 1 and 2 (S01, S02), unresolved across two more tech passes: all six references and four templates were read in one upfront batch before Phase 0's first artifact existed, rather than at each phase's own load-trigger.
- **Why**: Nothing in the text prevents front-loading; the "when you first need it" phrasing is a suggestion embedded in each link's surrounding sentence, not a structural constraint (e.g., a gate that would make front-loaded content unavailable or costly to hold).
- **Fix shape**: Unchanged from prior iterations' recommendation — no new fix shape found this run beyond what S01/S02 already proposed; noted here only so the total accurately reflects an uncorrected, recurring cost.

## Phase 0 specifics

- **What `scope.md` ended up looking like**: a `Last updated` line, one sentence of context (what was approved and when), and a five-column table — `Slug | Responsibility | Depends-on | Rank | Status` — with no header block (no Owner/Sign-off/Tracking) since Phase 0's text names only a `Last updated` line for this artifact. There is no template to check this shape against (friction #3) — it was assembled directly from Phase 0's descriptive paragraph, the only source available.
- **What the rank column meant in practice**: a plain 1–4 sequence matching both the order the user listed the four asks in and the order dependencies already forced (`notification-events` → `{notification-preferences, notification-history}` → `notification-digest`). Because this run only carried capability #1 through to completion, rank's actual purpose — breaking a tie when two or more capabilities are simultaneously unblocked (`Resuming work` → Large split: "where several qualify, take the one the approved rank names first") — was never exercised: after `notification-events` landed, both `notification-preferences` and `notification-history` become unblocked at once, which is precisely the scenario rank exists for, but the scenario's brief stopped before a next-capability pick had to be made. Rank was written correctly but tested only as a recorded value, never as a live decision procedure.
- **Whether dependency order was actually enforceable**: procedurally yes, but only by an agent's own discipline in reading the table — nothing mechanical (a gate, a lint check, a lockfile-style constraint) stops a future session from starting `notification-digest` before `notification-preferences` exists. Enforcement is exactly as strong as `Resuming work → Large split`'s instruction to "pick the next capability whose dependencies are `done`" and no stronger; this run respected it by construction (only one capability was ever in flight), so the real test of enforceability — a session tempted to jump ahead, or two sessions picking different unblocked capabilities at once — did not occur here.
