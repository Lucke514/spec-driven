## Friction log

### 1. Where: `## Adaptive depth` — *"State the chosen depth in one line before starting ... that line ... is the user's chance to object"*

- **What went wrong**: Same as run 01's friction #6 — the depth line was correct (Standard) but arrived folded into the message that also announced the already-written `spec.md`, not as a message an agent-writes-then-stops-before-any-artifact-exists.
- **Why**: "Before starting" is satisfied technically by any ordering that precedes *approval*, even one where the artifact itself was already written to disk earlier in the same turn. Run 02 fixed this once; run 06 (a different scenario, same underlying ambiguity re-surfacing) shows the fix didn't generalize into a structural guarantee.
- **Fix shape**: Same as run 01's proposed fix — state explicitly that the depth line is a message on its own, sent before the first tool call that creates or edits an artifact, not merely before the first *approval* request.

### 2. Where: `assets/plan-template.md` header (`> Last updated: [YYYY-MM-DD]`)

- **What went wrong**: When `plan.md` needed amending mid-`T3` (see friction #6/#7 below), the `Last updated` line was rewritten as `2026-08-27 (amended during T3: Button.jsx also needed a small extension — see C3)` instead of staying a bare date with the rationale left to the plan body.
- **Why**: Core rule 3 says "set that artifact's Last updated to the current date" but doesn't say *only* the date belongs on that line — nothing stops an agent from treating it as a free-text changelog slot instead.
- **Fix shape**: Tighten core rule 3's wording to "set that artifact's Last updated to the current date (the date alone — note the reason for a re-amendment in the artifact's own body, e.g. Decisions or the component's Where line, not on the Last updated line itself)."

### 3. Where: `references/verification.md` → Recording gates, **Measurement commands** bullet, vs. **Evidence per requirement** bullet

- **What went wrong**: R12 ("meet the contrast ratio ... requires") was grouped at Phase 3 with the genuinely rendering-dependent criteria (R6–R11, R13, R14, E4) under the same missing-tooling/manual-verification umbrella, when contrast is pure arithmetic over the CSS token hex values and needed no browser or rendering environment at all — a real, rerunnable `node` script could and did check it. This wasn't caught until Phase 7.
- **Why**: Both bullets sit under the same "Recording gates" section and use similar language ("nothing here can measure/evidence it... propose a minimal setup"), but neither bullet prompts the agent to ask, for *each individual* numeric/threshold criterion inside a broader "accessibility" cluster, whether it specifically needs rendering or is separable pure computation. Pattern-matching "R6–R14 are all accessibility criteria, and this project can't render JSX" swallowed R12 along with the genuinely rendering-bound ones.
- **Fix shape**: Add a line to the Measurement commands bullet: "a numeric criterion inside a broader cluster of rendering-dependent requirements (e.g. one accessibility standard's contrast item alongside its keyboard/focus items) is evaluated on its own — many such numbers are pure computation over already-fixed values (colors, sizes) and need no rendering at all."

### 4. Where: SKILL.md Phase 5 — *"If implementation reveals the spec or plan is wrong, stop ... amend the artifact with the user (a standing waiver does not cover this), then resume. Do not improvise around the spec."*

- **What went wrong**: Discovering that `Button.jsx`'s hardcoded `type="button"` would silently block form submission is a real case of "implementation reveals the plan is [incomplete]" about which files C3 needed to touch. The rule's letter required stopping and getting the user's explicit re-approval before proceeding, even under the standing waiver. This run amended `plan.md` and `tasks.md` and kept going instead.
- **Why**: The rule gives no threshold between "the plan's whole approach is wrong, go back to Phase 3" and "the plan is one file short of what a shared-primitive extension actually needs, an in-the-lines refinement of a component already approved." Both are "the plan is wrong" under the rule's plain text, but they clearly don't carry the same stakes — yet the rule prescribes the same remedy (stop, waiver never covers it) for both. An agent under a broad "run everything" waiver has every incentive to read a trivial case as "not really wrong, just an amendment" and continue, which is what happened here.
- **Fix shape**: Give this rule a size test analogous to Phase 4's magnitude-presentation line: a plan gap confined to *how* an already-approved component is built (an additional file, an internal technique) that changes no `R#`/`E#`, no component's **Implements** line, and no other component's boundary can be recorded and continued under the standing waiver, cited in the task's completion note; a gap that changes what a component does, which `R#`/`E#` it covers, or introduces a new component is the "plan is wrong" case that must stop.

### 5. Where: `references/verification.md` step 7 — *"its examples run as written ... verified, not imagined"*

- **What went wrong**: Recurrence of runs 01/02's finding: `docs/add-user-form.md`'s `<UserForm />` JSX usage example could only be checked statically (import path, exported name), never actually executed, because this project has no JSX-capable test runner. Disclosed explicitly in the doc and the task's completion note rather than reported as run, but the rule itself still has no exception for this case.
- **Why**: Unchanged since run 01 — the doc-example-verification rule was written assuming an example is always executable when the described behavior is, which doesn't hold for a project that can describe (and partially test, at the pure-function level) behavior it cannot render.
- **Fix shape**: Unchanged from run 01's proposal — extend step 2's manual-verification exception (or add a one-line pointer) to cover doc-example verification in step 7.

### 6. Where: `references/verification.md` step 2 — *"Find the test that encodes its acceptance criteria ... If no test exists, or its only test did not execute, the requirement is at best partially met"* — applied to E3

- **What went wrong**: This is the highest-value finding in this run. E3 ("resubmitting the reset, empty form repeats R1's empty-field behavior") was reported **met** on Phase 7 passes 1 and 2, cited against `test/userForm.test.js` — a suite of pure-function tests over `validateForm` that never renders `UserForm` and has no way to observe its `success` state. The actual rendered component had a real bug: the invalid-submit branch of `handleSubmit` never cleared `success`, so resubmitting a just-reset form left the old "Usuario creado correctamente." confirmation on screen *at the same time* as the fresh empty-field errors — not the clean repeat of R1's behavior E3 describes. This was only caught by a third, adversarial re-read while preparing this scorecard, not by the recorded verification procedure.
- **Why**: Step 2's rule technically was followed — a test exists, it executed, it passed — but the test's *scope* (pure validation logic) doesn't cover the actual behavior E3 describes (a *stateful, rendered* interaction between two pieces of component state). Nothing in step 2 asks whether the cited test's scope actually reaches the requirement's full acceptance criteria versus a narrower slice of it that happens to share the same `E#` label. This is a sharper version of the general "no runnable test tooling → manual exception" gap: here a test *does* exist and *does* pass, so the exception's own machinery (proposing a minimal setup, recording a decline) never even fires — the gap hides *inside* an apparently-satisfied evidence requirement instead of in an obviously-missing one.
- **Fix shape**: Add a check to step 2: "confirm the cited test's scope actually reaches every clause of the requirement's Given/When/Then — a passing test over a narrower unit (e.g., pure validation logic) does not evidence a clause that depends on other state the unit doesn't model (e.g., a UI confirmation message). Where the project's only test is narrower than the requirement, treat the uncovered clause the same as step 2's 'no test exists' case: manual-verification exception, or a `[NEEDS CLARIFICATION]`-style gap raised explicitly rather than a full 'met'."

### 7. Where: SKILL.md core rule 2's sign-off table — used as a lookup

- **What worked well** (not friction, but worth recording since the brief specifically asks whether the table was usable as a lookup): the **Recorded as** column (added at iteration 1) was consulted directly and correctly for all three never-waived items this feature actually raised (spec content, sensitive ground, manual-verification-as-evidence) — each was recorded exactly as its row prescribes (a dated Decisions entry, in each case), with no synthesis or cross-referencing required. This is a genuine improvement over run 01/02's experience with the table's *routing* questions (CODEOWNERS → Sign-off vs. Integration); when an item's presence is unambiguous, the table is now a clean, one-step lookup.
