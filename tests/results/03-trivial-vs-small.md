## Friction log

### 1. Where: SKILL.md → Adaptive depth, the Trivial row's own escape test ("If you could state the change as an `R#` with a Given/When/Then, it is at least Small")

- **What went wrong**: nothing, in this run — the classification landed correctly — but only after explicit deliberation between three readings (whole-Trivial, split, whole-Small) that the text does not resolve directly.
- **Why**: the sentence is written as if "the change" obviously means the whole thing under consideration, but a request that bundles a Trivial-shaped clause and a Small-shaped clause (common in real usage — "also rename this while you're at it") is never addressed. Phase 0's split logic exists for exactly this shape of question but is explicitly gated to Large ("bundles multiple capabilities that could each ship and deliver value on their own"), so an agent reasoning by elimination has to infer that sub-Large mixed-depth requests are never split — a rule that is true here but stated nowhere.
- **Fix shape**: add one sentence to the Trivial row or the three bullets under the depth table: "classify the whole request as one unit at its deepest qualifying clause; only Large's Phase 0 splits a request into separate artifacts." That single line would have made this run's correct answer traceable to text instead of to inference.

### 2. Where: SKILL.md Phase 5 ("self-review the diff against the junk-code checklist in [clean-code.md](clean-code.md) — read it now if this is the session's first self-review") — bullet order

- **What went wrong**: the rule sits as the second half of a compound sentence whose first half is about running gates ("Before marking a task done, pass the gates: run the task's verification step and every quality gate... with no new failures... then self-review the diff against the junk-code checklist"). All three tasks in this run were marked done after the first half only; the checklist was not opened until Phase 7's own mandatory sweep forced it.
- **Why**: the mechanical gates are named commands with a clear pass/fail the agent already has a habit of running (they came from the plan's Quality gates table, a concrete artifact); the junk-code self-review is a reference load plus a manual read-through with no artifact field recording that it happened per task — nothing forces evidence of it the way the Quality gates table forces evidence of the mechanical gates. It is easy to satisfy the sentence's first clause, treat the task as done, and never reach the second.
- **Fix shape**: give the per-task self-review the same kind of forcing function the gates already have — e.g. a `Clean-code check: ✅/hit` line in the task's completion note (`tasks-template.md` already has a `Notes` field that could require it), so a task closed without it is visibly incomplete rather than silently skipped.

### 3. Where: SKILL.md → Adaptive depth, Small row's artifact list vs. Phase 1's Surfaces/Operational-criteria bullets

- **What went wrong**: added a `## Open questions` header (not in Small's enumerated section list: header block, Objective, Requirements, Non-goals, Edge cases, Decisions, `## Tasks`) and folded the Surfaces/Operational-criteria analysis Phase 1 requires ("Name the surfaces... walk the row or checklist of each one you named") into Non-goals, because Small's table gives that analysis no named home once "Users & scenarios" is dropped.
- **Why**: Phase 1's substantive rules (surfaces, operational criteria, sensitive ground) apply at every depth — nothing exempts Small from them — but the Small row's artifact enumeration is a closed list of headers that has no slot for their output. An agent following Phase 1 literally produces content the Small template has nowhere to put.
- **Fix shape**: either add "(surfaces/operational-criteria coverage folds into Requirements/Non-goals — no separate header)" to the Small row, or give Small a one-line "Surfaces" field the same way it keeps a one-line Non-goals.

### 4. Where: SKILL.md core rule 2's sign-off table, row "Accepting a manual verification as a requirement's only evidence" + Phase 5's task-claim mechanic ("commit that claim before writing code — one commit, always, whatever the scan found")

- **What went wrong**: nothing incorrect — both rules were followed exactly as written — but their combined cost on a 3-task, 1-agent, 1-branch, 3-line change was 4 pure-ceremony commits (`claim T1`, `claim T2`, `claim T3`, plus the sign-off's own Decisions-entry overhead) against 4 commits that actually carried work.
- **Why**: this is the same tension run 01 flagged (friction #4) and iteration 2's advisor pass explicitly considered and rejected a solo-session exemption for ("claim-commit exemption... undecidable by a branch scan"). The design is deliberate, not an oversight — but it means every Small change this tiny pays the same fixed per-task commit tax as a multi-agent feature, with nothing in the text scaling it down.
- **Fix shape**: none proposed here — this is a known, considered trade-off, not a new defect. Recorded for the Proportionality section below rather than as something to fix blindly.

### 5. Where: SKILL.md → Adaptive depth, Small's phase list ("1, 2, 5, 6, 7 — plus Phase 3's tooling discovery, its minimal-setup proposal included; 0, 3, 4 skipped") vs. core rule 2 ("Phases 1–2 are one unit: never ask for approval while `[NEEDS CLARIFICATION]` markers remain")

- **What went wrong**: drafted the entire `## Tasks` section — gates, Base, Integration, overlap scan — into the same file that still carried an unresolved `[NEEDS CLARIFICATION]` marker, before asking the marker's question. No approval was requested while the marker stood (the rule that is actually stated), but Phase 3's folded content was written ahead of the marker's resolution, which the text neither licenses nor forbids.
- **Why**: at Small, "Phase 3's tooling discovery" has no independent stop of its own to anchor its ordering relative to Phase 2's clarify step — it is described only as additional content, never sequenced against the marker-resolution rule that governs the same file.
- **Fix shape**: one sentence: "at Small, resolve `[NEEDS CLARIFICATION]` markers before drafting the gates/tasks content that follows them in the same file" — or state explicitly that drafting ahead of an unresolved marker is fine, so this isn't left to be inferred either way.

### 6. Where: SKILL.md Phase 5 ("Write or update tests that encode the task's acceptance criteria — tests are the executable form of the spec") vs. core rule 6 / `clean-code.md` → Structure ("No speculative generality: abstractions... with exactly one current use and a hypothetical future one")

- **What went wrong**: nothing shipped incorrectly, but reaching the decision to *not* extract `handleSave`'s logic into a testable `src/lib/` module (mirroring `UsersTable`'s own sort/filter extraction, an established local convention) required weighing these two rules against each other with no tie-breaker in the text. A differently-tuned run could just as defensibly have built the extraction, producing a materially different diff (a new module, a new test file) for the identical spec.
- **Why**: both rules are legitimate and both point away from each other in exactly this shape of case — a component whose only untestable part is its JSX wiring, where the underlying logic *could* be made pure and tested, but doing so has no purpose beyond enabling that one test.
- **Fix shape**: add a line to `clean-code.md`'s speculative-generality bullet or to Phase 5: "extracting pure logic from an otherwise-untestable component solely to make it testable is not speculative generality — it has a current use (Phase 5's own testing requirement) — but is optional, not mandatory, where the project already accepts a manual-verification exception for the same class of gap elsewhere (cite the precedent)."

Net: **~40 lines of process artifact and ~3 commits per line of shipped code** for a request the user phrased as one sentence.
- **Would a real developer have abandoned the skill here?** Most likely right after the first artifact was presented — the full collapsed `spec.md` (header block, Objective, R1/R2 with Given/When/Then, Non-goals, edge cases, Decisions, a three-task breakdown with gate tables, Base/Integration/overlap-scan lines) plus a clarifying question about test tooling, all before a single character of code changed, for a request pitched as "change this text and disable the button while it saves." That is the first point demanding the user's active engagement rather than passive reading, and the ceremony-to-ask ratio is starkest there. A secondary abandonment point: seeing `claim T3` land as its own commit immediately before the one-line CHANGELOG edit it exists to protect.
