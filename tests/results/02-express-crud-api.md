`pg`, and `zod` are declared dependencies never installed. Every module needing them uses
`import type` (erased by Node's built-in TypeScript type-stripping, stable on Node 22.23), so
files execute without the packages present. `src/middleware/validate.ts`'s `schema` is a
hand-rolled, zod-shaped validator; `src/db/index.ts`'s `createMemoryDb()` is a hand-rolled
SQL-subset interpreter standing in for Postgres. `src/app.ts` and `scripts/migrate.js` do real
value-imports of `express`/`pg` and cannot execute here at all — by design, this makes the
migration genuinely unrunnable (the scenario's "DB unreachable" case) rather than merely slow.
TypeScript here is real `.ts` with type annotations (an improvement over run 01's plain `.jsx`),
but there is no real `tsc` offline — `checks.js typecheck` only confirms syntax strips cleanly
(`node:module.stripTypeScriptTypes`), never real type errors. This is disclosed in the fixture's
own `README.md` and in `plan.md`'s Quality gates table, not silently passed off as a real gate.

## Friction log

### 1. Where: `verification.md`'s 9-step Procedure (all of Phase 7) vs. SKILL.md → Resuming work → Artifact cross-check ("every spec `R#`/`E#`... appears in the plan's Requirement coverage table")

- **What went wrong**: The Requirement coverage table (`plan.md`) listed `E1/E2/E3 → C1, C2` from Phase 3 onward, but the actual HTTP-level `404`/`5xx` behavior those edge cases describe is produced by C3 (the routes), not the repository alone — C3's own component description never named E1–E3 either. This survived Phase 3 approval, Phase 5 implementation, and two full Phase 7 convergence passes (including the pass that fixed E1 by adding code to C3) without ever being caught.
- **Why**: `verification.md`'s procedure walks every `R#`/`E#` against code and tests directly (step 2) and never once revisits the plan's own coverage table to check it still names the right components — only SKILL.md's *Resuming work* section (a different, later-session-only trigger) checks the coverage table at all, and even then only for *presence* of an `R#`/`E#` somewhere in the table, never for whether the listed `C#`s are accurate. A gap discovered mid-Phase-7 that lands in a component the plan never attributed it to has no rule telling the agent to go back and fix the bookkeeping.
- **Fix shape**: Add a step to `verification.md`'s procedure (near step 6's inventory build, or as part of filing a `G#`): "if a gap's fix lands in a component the plan's Requirement coverage table does not already list for that `R#`/`E#`, amend the table and bump `plan.md`'s `Last updated` before closing the gap."

### 2. Where: SKILL.md core rule 2's sign-off table + `references/team-and-review.md` → Sign-off authority + → Integration (three separate sections, each independently referencing CODEOWNERS)

- **What went wrong**: Deciding whether `@platform-team`'s CODEOWNERS ownership of `src/db/**` belongs on the spec's Sign-off line or the plan's Integration line required synthesizing three sections that never cross-reference each other: Phase 1's Discovery checklist says CODEOWNERS feeds "which role must sign off" (citing core rule 2's table); core rule 2's table lists specific triggering events (irreversible data change, sensitive-ground `R#`, new dependency, etc.) that a merely-additive schema change under an owned path does not actually trigger; and Integration's own checklist separately says CODEOWNERS maps to "who must approve" the change set. Nothing states that a CODEOWNERS-named path *not* tied to one of core rule 2's specific triggers routes to Integration instead of Sign-off — an agent has to infer this by process of elimination.
- **Why**: The same discovered fact (CODEOWNERS names a role) legitimately feeds two different downstream artifacts depending on *why* the path matters, but the rule that decides which artifact is never stated as a rule — it has to be reconstructed from what core rule 2's table does and does not list.
- **Fix shape**: Add one sentence to Phase 1's Discovery bullet: "a CODEOWNERS-named role for a touched path goes on the plan's Integration line by default; it also goes on the spec's Sign-off line only when the path's change additionally trips one of core rule 2's table rows (e.g., an irreversible data change)."

### 3. Where: `references/team-and-review.md` → Discovery ("Branch-protection or required-check configuration held in the tree")

- **What went wrong**: This checklist item assumes a repo's required-review policy is discoverable by reading files in the tree. For a GitHub-hosted project using GitHub's native branch-protection UI (the overwhelmingly common case), that configuration is *never* a file in the tree — it lives in the platform's settings, invisible to a repo-only read. `plan.md`'s Integration line ended up asserting `@platform-team`'s approval is "required" for `src/db/**`, an enforcement claim that was never actually confirmable from the evidence available.
- **Why**: The checklist item is phrased as if "not found in the tree" reliably means "no policy exists," when for the single most common hosting platform it just as often means "the policy exists but isn't file-discoverable." The rule doesn't distinguish these two cases or hedge the resulting claim.
- **Fix shape**: Add a caveat to the Discovery bullet: "GitHub/GitLab native branch-protection rules are usually configured in the platform, not the tree, and will read as absent here regardless of whether they exist — phrase the Integration line as 'CODEOWNERS names `<role>`; enforcement could not be confirmed from the repo alone' rather than asserting the review is required."

### 4. Where: SKILL.md Phase 3 missing-tooling rule ("If a gate is genuinely missing, say so... propose a task adding a minimal setup") vs. `verification.md` step 2's manual-verification exception, applied per-requirement rather than per-gate

- **What went wrong**: The missing-tooling propose-or-decline flow was applied cleanly to `scripts/migrate.js` at Phase 3 (a gate-shaped, repo-wide question). But R6's specific gap — proving `requireAuth` is actually wired in front of `/tasks`, which needs a real HTTP call and thus a real `express` install — is not a *gate*, it's a single requirement's own evidence path, and nothing in Phase 3 prompts enumerating this kind of per-requirement execution gap the way it prompts enumerating the four core gates. It was only caught by rereading `verification.md` step 2's exact exception wording ("or the requirement's own test cannot execute here") during Phase 7, after the code was already written and Phase 3 had already closed.
- **Why**: Phase 3's missing-tooling proposal is framed entirely around *gates* (lint/format/types/tests/other CI checks) and *data-change mechanisms*; a requirement whose only possible evidence needs infrastructure no gate names (here: a running HTTP server) has no prompt anywhere before Phase 7 to surface that gap and ask the user about it in advance.
- **Fix shape**: Add a line to Phase 1 or Phase 3: "for a requirement whose evidence can only come from infrastructure this environment lacks (a live server, an external service), flag it at spec or plan time — even absent a named gate for it — the same way a missing quality-gate tool is flagged."

### 5. Where: `references/writing-specs.md` → Minimum shippable & deferral / `team-and-review.md` → Open follow-through ("Each is a dated Decisions entry naming when it lands and who owns it") vs. clean-code.md → Boundaries ("wider cleanups become new tasks proposed to the user")

- **What went wrong**: The tasks.ts/projects.ts duplication hit is a legitimate clean-code finding whose fix requires touching a file outside this feature's scope. Boundaries correctly says to propose it rather than smuggle it in — but when the user's answer is "later, don't touch it now" *without* naming an owner or a date, Open follow-through's own rule says that entry "is incomplete" — yet nothing tells the agent what to do when the user won't supply the missing pieces. The result is a Decisions entry that is honestly recorded but structurally non-compliant with the rule that governs it.
- **Why**: Every other "declined/deferred" path in the skill (deferral, waiver, accepted limitation) assumes the user's answer always comes with the owner+date the record needs. This is the one path (an out-of-scope cleanup surfaced mid-feature) where the user's most natural answer — "not now" — doesn't include either, and the skill has no fallback (e.g., default the owner to the session's user, or explicitly permit an owner-less entry flagged for later assignment).
- **Fix shape**: Add a fallback to Open follow-through: "if the user declines to name an owner or date, default the owner to the session's user and flag the entry `— owner/date pending` rather than leaving it structurally incomplete."

### 6. Where: my own execution (not a text defect) — G2's Acceptance criterion vs. its actual test

- **What went wrong**: G2's Acceptance criterion states all four handlers (`list`/`create`/`update`/`remove`) return `500` on a failing `Db`; only `list` was tested. The Phase 7 report cited this as `E1: met` without qualifying that three of the four claimed behaviors were inferred from the shared `catchAsync` wrapper's construction, not independently verified.
- **Why**: `catchAsync` is applied uniformly, so the risk is low, but `verification.md` step 2 is explicit that a verdict rests on "the test that encodes its acceptance criteria," not on code-reading confidence about a shared implementation detail.
- **Fix shape**: Not a skill defect — a self-correction for a future pass: either narrow G2's Acceptance to what was actually tested, or add the three remaining cases before marking it done.
