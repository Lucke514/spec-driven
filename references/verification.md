# Verification & convergence

Detailed procedure for Phase 7 (Verify). Load this when every task is checked or waived, or when resuming a feature whose code may have drifted from its artifacts.

## Procedure

1. **Re-read `spec.md`** end to end — not from memory. The spec as written is the checklist.
2. **Walk every requirement and edge case** (`R#`, `E#`). For each one:
   - Find the code that implements it. Cite real paths.
   - Find the test that encodes its acceptance criteria. Run it, and read the runner's own report of it: a test recorded as skipped, ignored, `xfail`, disabled, or filtered out by the run's selectors did not execute and is not evidence, however green the suite around it is.
   - If no test exists, or its only test did not execute, the requirement is at best *partially met* — regardless of how the code looks.
   - Exception — no runnable test tooling: if the project has no test runner, none that can execute in this environment, or the requirement's own test cannot execute here (a disabled integration test whose external dependency is unavailable), and the user declined making it runnable or the proposed minimal setup (from `plan.md`, or from the collapsed `spec.md`'s `## Tasks` section for Small features; the refusal recorded as a Decision in `spec.md`), the requirement may reach *met* through a manual verification the user approved as that requirement's evidence — an explicit sign-off, which a standing waiver does not cover. Cite the exact commands or actions run and their observed output as Evidence. This exception never applies when tooling exists and the test is merely missing.
   - **Measured requirements** — for an `R#` stating a number, evidence is the measurement command recorded in `plan.md` next to the quality gates (Small: next to the tasks in the collapsed `spec.md`), run now, with its observed value **and the conditions of that run** (environment, data scale, concurrency, run count) cited against the requirement's threshold, confirming the conditions recorded in the plan still hold. That is a passing check, not the manual exception above: the test-encoding rule governs behavioral criteria. A value measured under conditions the requirement does not describe is *partially met*, never **met** — name the condition that was missing, and propose moving the criterion to an `SC#` if nothing here can reproduce it.
   - **Stored-data requirements** — an `R#`/`E#` whose behavior depends on a change listed in the plan's **Data changes** also cites that the recorded migration/backfill command ran against the **Target** the plan names, its observed output, the plan's **Data integrity** check with its observed result (not just the command's exit), and the reversal where the plan recorded one, exercised with rows present. A run against a shared, staging, or production datastore is a stop-and-ask, never evidence the agent produces on its own. The report then carries a one-line `Data & delivery:` summary — omit that line when the plan records `— none` and `— ships with the normal release`.
   - **Delivery-switched requirements** — where the plan's **Delivery** names a flag or config switch, evidence for an `R#`/`E#` names the state it was produced under (which flag setting, which config value), the same way a measured requirement names its run conditions; each state the feature ships in has its own evidence or an explicit Non-goal, and a state with neither is at best *partially met*. Where the plan records an off path, its exercised run (feature on → off → pre-feature behavior returns, plus what work survives the flip) goes on the report's `Data & delivery:` line, together with the stage the feature is at where the plan records **Rollout stages**.
   - **Third-party-backed requirements** — where an `R#`/`E#`'s behavior originates in a third party (a dependency call whose result the criterion asserts, or an external service the feature calls at runtime), its evidence names the stand-in the test ran against, as recorded on the plan's **Dependencies** line: a hand-written fake, a provider-published fixture or contract artifact, a recorded real response, the provider's sandbox, or the real service. Where the stand-in's shape is asserted by this repo alone, with nothing tying it to the provider's own contract, the verdict is at best *partially met* — name the missing tie, and propose moving the criterion to an `SC#` naming the environment where the real integration is exercised. A run against a live paid or production third-party account is a stop-and-ask, never evidence the agent produces on its own, exactly as for a shared datastore.
   - **Declared shortcuts** — a requirement whose implementation the implementer declared substandard (SKILL.md → Phase 5: a dated Decisions entry naming what was traded, the proper version, and its owner) is still **met** where the behavior ships and its test passes — the verdict is not the whole story. List every such Decisions entry from this feature on the report's `Shortcuts declared:` line, naming the `T#`, what was traded, and who owns the proper version, so the approver sees them at the gate instead of finding them later in spec history.
3. **Assign a verdict per requirement**:

   | Verdict | Meaning |
   |---|---|
   | **met** | Behavior implemented; acceptance criteria encoded in a test that executed and passed — or, where the user declined test tooling, in an approved manual check with its output cited |
   | **partially met** | Implemented but criteria not fully covered (missing edge case, missing test) |
   | **not met** | Not implemented, or the verification fails |
   | **spec drift** | Code deliberately does something different from the spec |
   | **superseded** | Another feature's spec replaced this requirement — it carries `— superseded by …` in `spec.md`, annotated with the user's explicit sign-off (a standing waiver does not cover it); evidence is the successor's `R#`. Nothing is re-verified and no gap is filed |
   | **deferred** | Cut from this change set by a dated decision on record — the requirement carries `— deferred (Decisions YYYY-MM-DD, owner <who>)` in `spec.md` and an owner in the open-follow-through path ([team-and-review.md](team-and-review.md)). Evidence is that Decisions entry. Not verified, not a gap, never re-filed. Deferral needs the user's explicit sign-off (a standing waiver does not cover it), and a requirement inside the spec's **Minimum shippable** line cannot take this verdict — cutting into that set cancels the feature |

4. **Run the full verification suite** — every `Verify:` command from `tasks.md`, plus every quality gate recorded in `plan.md` (tests, lint, format, types, and every other gate recorded there). *(Small features: both the `Verify:` commands and the gates live in the collapsed `spec.md`.)* Compare each gate against the baseline recorded in `plan.md` → Quality gates: the gate **passes** when it shows no new failures relative to that baseline. Attribute every failure absent from the baseline before calling it new: re-run that check on the current tree **and**, always, with the feature's changes removed (stash, or a worktree at the recorded **Base**) — the base-tree control is never skipped, whatever the re-run here shows. Fails there too → `pre-existing`. Intermittent there → `flaky`: add it to the baseline as nondeterministic, say so in the report, and never block the task on it. Reproduces at HEAD but repeated runs on that untouched tree never reproduce it → **new**, even when it only fails on some runs here: flakiness the feature introduced is a bug (concurrency `E#`s are exactly where it hides), never a baseline entry. Any baseline entry added during Phase 7 is written back into `plan.md` → Quality gates with the runs that justify it and that artifact's `Last updated` bumped — the report alone is not the record. Compare a baseline recorded as a count (a lint backlog too large to enumerate) per file and per rule, never by diffing line-anchored reports — an insert shifts every line below it and manufactures phantom hits. A rise in the test gate's skipped count — or a drop in its executed or passing count — against the baseline is a new failure, not a pass: a suite green because its tests were disabled, deleted, or loosened has verified nothing (step 2). Deleting or weakening a failing test is never how a gate passes: account for every pre-existing test this feature removed, disabled, or weakened on the report's `Tests removed:` line, and unless the removal is itself a behavior change an `R#` specifies, get the user's explicit sign-off for it — a standing waiver does not cover it. List pre-existing failures in the report flagged `pre-existing`; they may be proposed as a separate fix task with the user's approval, and never block convergence. If no baseline was recorded, reconstruct it by running the gates on the pre-feature tree (base branch or stash) and say so in the report. If `git merge-base HEAD <the branch named in the plan's **Base** line>` no longer equals the recorded **Base** SHA, the branch was rebased or the base merged in and the baseline is stale — re-run the gates on that current merge base to refresh it, update the plan's **Base** SHA (and its branch name if that changed), and note the re-baseline in the report; failures the upstream introduced count as `pre-existing`, not new. A failure that traces to another feature's work is external the same way, committed or not: attribute it over the failing paths with `git log`/`git blame` before calling it new — if the change that introduced it is neither on this feature's branch nor carries this feature's `<slug>: ` commit prefix (a sibling's commits on a shared branch, or its uncommitted edits in the same tree), flag it in the report for that feature's own Phase 7, treat it as `pre-existing` here, add it to the baseline, and never block on it — or, while that work is still uncommitted, ask the user to commit or stash it and re-run the gate. A gate the plan records as **pipeline-only** is evidenced by that pipeline's run on this change set — cite the run's identifier and its result, judged by the same no-new-failures comparison; step 2's manual-verification exception never covers it, because the check does run, just not here. Where no such run exists for this change set yet, report the gate as `pending` and do not exit the convergence loop on it, unless the user explicitly accepts the pass without it — recorded as a Decisions entry in `spec.md`.
5. **Sweep the full diff for junk code** — one pass over the feature's change set (built as described in step 6), against the checklist in [clean-code.md](clean-code.md). Any hit is a gap, same as a failed requirement.
6. **Delete unused generated code** — everything the feature added must be reachable, or it goes:
   - **Build the inventory first.** It is the union of (a) every `Files` entry across the feature's `T#`/`G#` tasks and (b) where the repo uses git, the feature's change set: `git diff <base>...HEAD` when the feature has its own branch, where `<base>` is the **Base** SHA recorded in `plan.md` → Quality gates (for Small features, next to the gates in the collapsed `spec.md`) — if no Base was recorded, ask the user for the last commit that predates this feature's work; never guess `main`, or — when its commits are slug-prefixed on a shared branch — the commits whose *subject* begins with the prefix `<slug>: ` (`git log --format='%H %s' <base>..HEAD | grep '^[0-9a-f]* <slug>: '`) and `git show` over exactly those commits; an unanchored search over full messages also drags in commits that merely mention the slug in a body and sibling slugs that begin with it (`billing` vs `billing-invoices`). Both git modes read committed history only — add the uncommitted work as well (`git status --porcelain`, including untracked files, plus `git diff` against the base), since the feature's work is often still sitting in the working tree when Phase 7 runs. Count only paths this feature's tasks or plan name — in the committed modes as much as in the uncommitted one; everything else stays out of the inventory: paths and commits another in-flight or landed feature's `specs/<slug>/` artifacts claim (find those specs as in Phase 3's overlap scan — every `specs/*/` in the repo, plus the other active branches, so an empty result means "none"), everything a merged sibling branch brought into `<base>...HEAD`, and unclaimed local state that lives in the tree year-round (personal config overrides, dumps, long-lived untracked scratch files) alike — list the excluded paths on the report's `Excluded from inventory:` line, each naming its owner (the claiming feature's slug, or `unclaimed local state`), and never file gaps against them. A change-set path that no task or plan names but that no other feature claims and that is not unclaimed local state is a bookkeeping miss, never an exclusion: add it to the inventory **and** to its owning task's **Files** line. That is why Phase 5 requires one mode or the other. Where the two disagree, reconcile by reading the code; never delete on a diff line alone. With no git and no reliable Files entries, say so in the report and scope the sweep to the paths the tasks name. Documentation and specification artifacts are exempt from the reachability requirement — `specs/<slug>/*`, `docs/<slug>.md`, and README/CHANGELOG edits are never deletion gaps; step 7 verifies those instead.
   - List every symbol, file, export, and dependency in that inventory.
   - For each one, confirm something actually reaches it: production code, a test that verifies real behavior, an entry point (a route, a CLI command, a public API, or a framework/config registration — a scheduled or queued job declared in configuration, a signal/event handler, a plugin or DI registry entry, an admin/router registration, or any symbol named by dotted-path string in config; of these only a public API must be documented in `docs/<slug>.md` — and *public API* means a surface this repo publishes to consumers it does not control (an exported package boundary, a released artifact's interface, a REST/CLI/queue contract), never a language visibility keyword: `pub`, `public`, and Elixir's `def` alike are no evidence of reachability in any language, so name the consumer or the publication boundary), a contract the runtime or compiler dispatches on (a behaviour or interface callback on a registered module, such as OTP `handle_call`/`handle_info`/`terminate`; a trait/protocol/typeclass implementation; a lifecycle or operator hook such as `Drop` or `Display`, derive-generated impls included) — whose Evidence is the contract plus the registration or use site of the *type*, not a caller of the function — or a runner that consumes it (a recorded quality-gate command, the build, or the project's migration/seed runner) — cite that command or runner as Evidence.
   - Unreached by any of the above → file a gap task to **delete it** — code, its tests, its exports, and any dependency only it used. Deletion is the default, but never automatic: a deletion gap is implemented only after the user explicitly confirms it — a standing waiver does not cover deletions. It survives only if the user explicitly promotes it to a requirement in `spec.md`; or it implements a requirement the spec carries as `— deferred` — code named by a live requirement is not code reached by nothing, so the choice is the user's and is put to them explicitly: keep it, with the deferral's Decisions entry cited as its Evidence and the kept paths named on that entry so later passes do not re-file it, or delete it now and rebuild when the deferral comes due; report the choice on the `Dead-code sweep:` line either way, so "kept for a deferred requirement" is a recorded state and never a silent one; or a component (`C#`) in another feature's or capability's **approved** `plan.md` (e.g. a sibling capability from the same Phase 0 split; find those plans as in Phase 3's overlap scan, other branches included) names it — cite that `C#` as Evidence instead of filing a deletion gap; or it sits on a surface this repo publishes outside the analyzed tree — a library artifact other repos consume, a sibling deployable, ops/admin/JMX tooling, or dispatch named in external or DB-held configuration — where the Evidence is that publication boundary, confirmed with the user. Dead-code tooling flags framework-registered symbols as unreached — check the registration, of the module or type as much as of the function itself, before filing. Every deletion gap states its scope of analysis in one line — what was actually searched (this tree, plus any registries or config sources read) — so `unreached` reaches the user as a bounded finding, never an unqualified fact.
   - Sweep the other direction too: any **pre-existing** symbol whose last caller this feature removed or rewrote is dead code the feature just created. File a deletion gap task for it as well, flagged `pre-existing` so the user sees the deletion reaches beyond the feature's own code. Sweep dependencies the same way: a **pre-existing** third-party dependency whose last import this feature removed or rewrote is dead weight the feature just created — a manifest entry is neither a symbol nor a path the tasks name, so nothing else will collect it. Confirm the manifest and the source hold no remaining importers, then file the deletion gap over the manifest entry, the lockfile entry, any vendored copy, and any attribution or notice file kept for it, flagged `pre-existing` like the symbol case.
   - **Walk it code-to-spec as well**: behavior in the change set that something does reach but that traces to no `R#`/`E#` — and is not plumbing for one — is scope creep, and the spec wins. Same promote-or-delete choice as unreached code: file a gap to delete it, or have the user promote it through a `spec.md` amendment.
   - **Check the plan's Reuses lines**: new code in the change set that duplicates behavior an existing module already provided — the thing a component's **Reuses** line should have named — is a gap: file it to replace the new copy with a call to (or an extension of) the existing code, then let the dead-code sweep collect the copy.
   - Per-diff checks miss these: a helper used when written becomes an orphan when a later task removes its caller. That is why this runs over the whole change set at the end.
   - Use the ecosystem's dead-code tooling when available (e.g. `knip`/`ts-prune` for TS, `vulture` for Python, `deadcode` for Go, compiler dead-code warnings — which exempt exported items in library crates, so a silent build is no evidence either); confirm hits by reading before deleting — dynamic dispatch and reflection produce false positives.
7. **Check the documentation** — `docs/<slug>.md` exists (Small features: the README or doc-comment update the depth rules allow counts as the doc artifact — check that instead), describes actual behavior, its examples run as written, and README/CHANGELOG were updated where applicable. Missing or stale docs are a gap. Where the plan's **Delivery** is not `— ships with the normal release`, the spec carries an operational-signal `R#`/`E#`, or the plan's **Dependencies** line records an external service called at runtime, the page's **Operating** section exists and matches what shipped — the switch and how to turn the feature off, the signal and where it is read, what to do when it fires, and, for a runtime external service, that service, the contract version the integration targets, and where its status is read; a missing or stale Operating section is a documentation gap like any other. A Decisions entry that binds beyond this feature — an architecture pattern, a dependency other code will share, a cross-cutting convention, a targeted contract version — with no entry in the project's own decision record, where the repo keeps one (`docs/adr/`, `decisions/`, an RFC folder), is a documentation gap like a stale Operating section.
8. **Walk the spec's Success criteria (`SC#`), then report.** Verify each `SC#` that is checkable now and cite its evidence; list the rest in the report as pending rollout checks — pending criteria inform the reader but do not block convergence. A pending `SC#` whose signal this feature itself produces is pending only on its *value*: verify the emission now — cite the signal appearing with the expected shape, from its test or an observed run here — and report the criterion as pending on that signal. A pending `SC#` that reads a signal nothing in the change set or the existing system produces is not pending but unverifiable: file it as a gap (`G#`), same as a *not met* requirement. *(Small features: the collapsed `spec.md` keeps no Success criteria section — skip this walk and omit the report's `Success criteria` line.)* Report the verdict table to the user before doing anything about the gaps.
9. **Check the change set's integration state** — before reporting, read the plan's **Integration** line (Small: next to the tasks in the collapsed `spec.md`). Where it records a review-gated path: is this change set merged into the branch the plan's **Base** names (`git merge-base --is-ancestor HEAD <that branch>`), and are the required approvals on record? Report the answer on the report's `Integration:` line — `merged (<identifier>)` with the approvals cited, `pending review (<identifier>)`, or `not opened yet` — together with any `pending sign-off: <role>` the spec's Status line carries. Where the line records `— direct commits to the base branch`, report `direct commits — no review policy`. A pending state informs the reader and blocks neither the report nor the convergence loop; it blocks only the terminal **implemented** status (SKILL.md → Phase 7). Any edit made to the change set after a converged pass — review fixes included — invalidates that pass's report: run the procedure again. Rules in [team-and-review.md](team-and-review.md).

## Handling gaps

- **Diagnostic passes** — when the pass runs with unchecked `T#`/`G#` tasks remaining (a resume drift check, regenerated artifacts, or a reopened feature; a task marked `- [~] Waived` or `- [>] Deferred` is closed and never counts as unchecked), its verdicts are diagnostic, not a convergence attempt: file no `G#` for a verdict an existing unchecked task already covers — cite that task in the report instead. Report the drift verdicts, the partial verdicts, and any refreshed baseline, then hand back to Phase 5 at the first unchecked task rather than entering the convergence loop. On regenerated artifacts, a **met** verdict is what licenses checking that task's box.
- **not met / partially met** → append tasks (IDs `G1`, `G2`, …, same format as normal tasks) to the `Gaps found in verification` section of `tasks.md` — for Small features, under the collapsed `spec.md`'s `## Tasks` section. Get approval, then implement via Phase 5.
- **spec drift** → decision point for the user, never yours alone:
  - If the code's behavior is *better*: amend `spec.md` (and its Decisions section) to match, with the user's approval.
  - If the spec was right: file a gap task to fix the code.
  - Either way, spec and code must agree when you finish. Silent drift is the failure mode this whole workflow exists to prevent.

## Convergence loop

After gap tasks are implemented, run the procedure again. Exit when a full pass yields **met** on every requirement and edge case (`R#`, `E#`) — except any the user accepted as a documented limitation, annotated as **superseded**, or annotated as **deferred** by a dated decision naming its owner — with zero new gaps. Two consecutive passes that keep finding new gaps usually mean the spec is ambiguous — go back to Phase 2 rather than iterating blindly. If a requirement cannot reach *met* by any available means, stop the loop and put the choice to the user (accept it as a documented limitation, defer it out of this change set with a date and an owner, change the spec, or add the missing tooling); a standing waiver does not cover this choice — never keep re-running the pass on an unreachable verdict. An accepted limitation is recorded as a Decisions entry in `spec.md` **and** annotated on the requirement itself — `— accepted limitation (Decisions YYYY-MM-DD)` — after which later passes report its recorded verdict and never re-file a gap for it. A gap the user explicitly declines to fix is closed as **waived**: record the choice and its rationale as a Decisions entry in `spec.md`, replace that `G#` task's `- [ ] Done` with `- [~] Waived — YYYY-MM-DD, why` in `tasks.md`, and list it in the final report — a waived gap does not block exit and is not re-filed on later passes.

## Report format

```markdown
## Verification report — [feature] — [date]

| Req | Verdict | Evidence |
|---|---|---|
| R1 | met | `src/auth/login.ts:42`; test `login.test.ts` ✅ |
| R2 | partially met | implemented, edge case "empty email" untested |
| R3 | spec drift | code rate-limits per IP, spec says per account |
| E1 | met | empty-email path rejects at `src/auth/login.ts:58`; test `login.test.ts` ✅ |

Gates: `npm test` ✅ 82/84 (2 pre-existing failures + 3 skipped, unchanged; `sessionSweep` flaky — fails on the base tree too) · lint ✅ · format ✅ · types ✅ · `npm run test:a11y` ✅ · `npm audit` ✅ (project gates) · Pipeline: `contract-tests` ✅ (run 4821 on `9f2c1ab`) · coverage ⏳ pending — no run for this change set yet
Tests removed: 1 — `login.test.ts::legacy password path`, removed with the legacy path R1 replaces (user approved 2026-05-04)
Clean-code sweep: 1 hit — commented-out block in `src/auth/session.ts:88`
Shortcuts declared: T7 — saved-card last-4 denormalised on the order row instead of the token vault C3 describes; proper version owned by `@lead`, tracked as `PROJ-813` (Decisions 2026-05-06)
Dead-code sweep: 1 hit — `hashLegacy()` in `src/auth/hash.ts` unreachable since T4 dropped its caller (scope: this tree + `config/`; no published-artifact consumers)
Excluded from inventory: `packages/api/src/audit/*` (audit-log, uncommitted; 1 gate failure traced to it) · `dump.sql` (unclaimed local state)
Docs: `docs/user-authentication.md` ✅ · README updated ✅ · examples run ✅
Integration: pending review — `PR 482`, 1 of 2 required approvals (CODEOWNERS `src/auth/` pending) · spec carries `pending sign-off: security architect` (E3)
Data & delivery: migration `add_archived_flag` applied, reverted with rows present, re-applied on scratch database `app_scratch` ✅ · integrity: 40,132,904 rows before/after, invariant query returns 0 ✅ · backfill re-run twice, unchanged · seed `profile_visibility` idempotent ✅ · flag `pricing_v2` retirement owned by T9 · `pricing_v2` on→off→on exercised, pre-feature pricing returns ✅ (nothing to undo) · R2 evidence produced with the flag on; off state covered by R1 ✅ · config `PRICING_KEY` present in staging and production; absent → E4 fallback ✅ · rollout at stage 2/4 (25%, advance at ≥ 99.5% checkout success over 24h — SC2)
Success criteria: SC1 verified (p95 < 200ms in staging) · SC2 pending rollout check
Superseded: R4 — replaced by `specs/shared-money-type/spec.md` (successor R2)
Deferred: R4 — cut from this change set 2026-05-04, owner `@lead`, tracked as `PROJ-812` (Decisions 2026-05-04); C4's partial implementation kept by the user's choice — see `Dead-code sweep:`
Waived: G1 — filed on a previous pass; user declined deletion of `legacyExport()` (Decisions 2026-05-04) · R6 — accepted limitation, 30-day restore not checkable here (Decisions 2026-05-04)
Gaps filed: G2 (R2 edge-case test), G3 (R3 — pending user decision), G4 (junk-code hit), G5 (delete `hashLegacy` + its tests)
```

Report this block to the user, then append the same block — dated — to the `Verification reports` section at the end of `tasks.md` (Small features: at the end of the collapsed `spec.md`'s `## Tasks` section). One block per pass, newest last; never overwrite an earlier pass.
