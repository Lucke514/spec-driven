# Verification & convergence

Detailed procedure for Phase 7 (Verify), its terminal status and Audit mode, plus the rules for recording the quality gates. Load this when recording the plan's gates, when every task is checked or waived, when resuming a feature whose code may have drifted from its artifacts, or when auditing code against a spec with no plan or tasks.

## Recording gates

How the plan's Quality gates table is filled (at Small, the same lines next to the tasks in the collapsed `spec.md`). Phase 3 records each row's gate, command, and `Where`; the baseline run, **Base**, and measured values come at Phase 5's start. Read this at both moments and whenever a row changes.

- [ ] **One row per gate, per package** — in a monorepo, record one row for each package the feature touches: gate kind plus package, its own command scoped to that package, its own baseline.
- [ ] **Read-only commands only** — a recorded command reports, it never rewrites the tree. Record a writing tool's check form (`cargo fmt --check`, `black --check`, `prettier -c`), never its default (`cargo fmt`, `black .`, `prettier -w`): a formatter gate that always exits 0 is not a gate.
- [ ] **The baseline run** — at the start of Phase 5, run each command once on a tree holding none of this feature's work. Where a diff already exists (re-classified work), stash it and measure without it, or measure at the ref this feature will start from. Confirm no *other* session's uncommitted work is present first — a sibling's broken edits recorded here become this feature's `pre-existing` failures and outlive the session; where they cannot be moved, record the baseline `provisional` and say so in the plan. The baseline is the run's pre-existing failures (enumerated, or a total where the backlog is too large to list) plus, for the test gate, its executed and skipped counts. Gates are judged as *no new failures*, not absolute zero.

  **The Baseline cell carries what the command printed** — the enumerated failures, or the counts it reported (`84 selected, 82 passed, 2 failed, 3 skipped`; `8317 warnings across 214 files`) — never an adjective. `clean` is a claim; `84 selected, 0 failed` is a reading, and only a reading can be compared against later. A cell holding no count and no named failure was not measured: say so as `not measured` and treat every verdict that would compare against it as void until it is.
- [ ] **Flaky failures** — a gate that does not reproduce its own result is nondeterministic: a failure a re-run on the untouched tree does not reproduce belongs in the baseline too, marked `flaky`.
- [ ] **Base** — record the base branch this feature starts from and the commit that run measured on (`git rev-parse HEAD` on the untouched tree) as the plan's **Base** line. Name a branch that still resolves later (`main`, `release/2.4`), never a bare SHA or `HEAD`. **The rebase test** later passes run on it has one form per topology, and the plan's **Base** line says which applies:
  - *Dedicated feature branch* — `git merge-base HEAD <that branch>` no longer equals the recorded SHA → the branch was rebased or the base merged in.
  - *Slug-prefixed commits on the shared branch* — `HEAD` **is** that branch, so the merge-base test can never fire: test instead that the recorded SHA is still an ancestor (`git merge-base --is-ancestor <Base SHA> HEAD`) and that it still names the same commit content; a failure means the shared branch was rewritten under the feature.
  - *No VCS, no commits yet, or a shallow history that resolves no merge base* — record `Base: — no resolvable history (<the check> → <its output>)` — the check being the one that establishes it (`git rev-parse HEAD`, `git rev-parse --is-shallow-repository`, or the absence of a VCS), cited as run, since this is the cheapest path through Phase 7 in the skill. A shallow clone must not record a grafted SHA: it makes every later pass diagnose a phantom rebase. Every rule that reads **Base** (the rebase test, step 4's base-tree control, step 6's change-set inventory, step 9's integration check) is then skipped, and the report says so on each affected line.
- [ ] **Where it runs** — `here`, or `pipeline-only` where the project enforces the check on every change but its credentials or infrastructure live in the pipeline. A pipeline-only gate is a recorded gate, not missing tooling and not the non-executable case below: no local baseline (record `—`), evidenced at Phase 7 from that pipeline's run on this change set by the same comparison (step 4). Step 2's manual exception never covers it.
- [ ] **A command that cannot execute at all** — missing service, dependency, or config; a test run that collects nothing because a database is unreachable — has no baseline and is never recorded as one: ask the user to make it runnable, or record their refusal as a Decisions entry in `spec.md` so step 2's manual exception applies.
- [ ] **A gate lacks tooling** only when nothing in the project can perform its check. In *statically typed* compiled languages the build command is the type gate (`go build ./...`, `cargo check`); where the language compiles without type-checking (Elixir, Erlang, Clojure) the build is no type gate — record the project's configured analyzer (`mix dialyzer`) instead, and treat the gate as genuinely missing only when none is configured. Where one is genuinely missing, say so in the plan and propose a minimal-setup task; never adopt heavy tooling uninvited, and a check this project never ran is not a missing gate — proposing one is its own spec discussion. If the user declines, record the refusal as a Decisions entry in `spec.md`: step 2's manual exception depends on it.
- [ ] **Measurement commands** sit next to the gates under the same rules, on the plan's **Measurements** line: for every requirement stating a number, the command that measures it, its value at the baseline run, and the conditions of that run (environment, data scale, concurrency, run count). Discover benchmark/profiling tooling as you discovered the gates. Where nothing here can measure it — or nothing here reproduces the conditions the number actually means, so the command measures a different question (toy data, a single run, a laptop for a production p95) — the missing-tooling rule applies: propose a minimal setup, or record the refusal and move the criterion to an `SC#` naming its measurement method and environment ([writing-specs.md](writing-specs.md) → Measured criteria).
- [ ] **Evidence per requirement** — the gates cover every task; this covers every requirement. With the gates recorded, walk the spec's `R#`/`E#` once and fill the plan's `## Evidence per requirement` table, one row each: the test encoding its criteria, the measurement command for a number, the stand-in for a third-party call, or the manual check where the project has no runner — plus whether that evidence exists today. Step 2 reads this table. Where nothing here can produce the evidence — a criterion needing a real HTTP call, browser, or device — the missing-tooling rule applies **here, in Phase 3**: propose a minimal setup, or record the refusal as a Decisions entry in `spec.md` so step 2's manual exception applies. Found at Phase 7 instead, it costs a requirement that cannot be evidenced at the gate.
- [ ] **Stand-ins are tied or accepted here** — where a row's evidence is a stand-in for a third party (a hand-written fake, a provider-published fixture or contract artifact, a recorded response, a sandbox — as the plan's **Dependencies** line records it), record on that **Dependencies** line either the tie to the provider's own contract (which check re-confirms the stand-in's shape, and how often) or the user's explicit acceptance of a stand-in this repo asserts alone, approved with the plan. Settle it now: an untied, unaccepted stand-in caps its requirement at *partially met* forever, and no implementation closes that gap.

## Procedure

1. **Re-read `spec.md`** end to end — not from memory. The spec as written is the checklist.
2. **Walk every requirement and edge case** (`R#`, `E#`), starting from its row in the plan's `## Evidence per requirement` table. A gap noticed mid-walk is **reported, not fixed on the spot**: note it, finish the walk, let Handling gaps route it — a fix written before the verdict table exists is an unreviewed change to the change set being verified. For each one:
   - Find the code that implements it. Cite real paths.
   - **The citation contract.** Evidence names the **test case** and the **assertion** that encodes the criterion — `login.test.ts::"rejects after 5 failed attempts" — expects 429 + lockUntil set`, never a bare file path — and the criterion clause each one answers. A requirement with several clauses needs an assertion per clause: a test that exercises the subject but cannot observe the state the criterion is about — it never renders the component, never reads the row, never inspects the response body — does not encode it, whatever it asserts. Run it and **quote the runner's own line for that case on the evidence row** — `1 passed` for that node id, or whatever your runner prints for a single selected case — so the citation carries a reading and not only a claim; a citation without it is an unfinished pass, exactly like an absent report line. A test recorded skipped, ignored, `xfail`, disabled, or filtered out by the run's selectors did not execute and is not evidence, however green the suite around it.
   - **Never carry a verdict forward.** `unchanged from pass 1` is not evidence. Every pass re-cites and re-runs; a verdict copied from an earlier block is void, and the pass that copied it has not converged.
   - **Negative control for the Minimum shippable set.** For each `R#`/`E#` inside the spec's **Minimum shippable** line, show the cited assertion actually fails when the behavior is stubbed out or reverted — a test that passes either way encodes nothing. Cite the observed failure. Where the requirement's only evidence is an approved manual check (the exception below), the control is that same trace run with the behavior stubbed or reverted, its observed output cited. Where no stub can be produced at all, **name the construct that makes it impossible** — the type signature, the exhaustiveness check, the compile-time constant, the schema the tooling rejects — in one line on the report: "cannot be stubbed" without a named construct is not an escape, it is an unrun control.
   - If no test exists, or its only test did not execute, the requirement is at best *partially met* — regardless of how the code looks.
   - Exception — no runnable test tooling: if the project has no test runner, none that can execute in this environment, or the requirement's own test cannot execute here (a disabled integration test whose external dependency is unavailable), **or the requirement's subject is declarative — configuration, infrastructure, a schema the project applies through its own tooling — and no runner in the project asserts it**, and the user declined making it runnable or the minimal setup Phase 3 proposed (the refusal recorded as a Decision in `spec.md`), the requirement may reach *met* through a manual verification the user approved as its evidence — or, in the declarative case, through the project's own validate/apply command against the target the plan names. Record that sign-off as a dated Decisions entry and cite it on this pass's report with the exact commands run and their observed output. Never applies when tooling exists and the test is merely missing.
   - **Measured requirements** — for an `R#` stating a number, evidence is the measurement command recorded in `plan.md` next to the quality gates (Small: next to the tasks in the collapsed `spec.md`), run now, with its observed value **and the conditions of that run** cited against the requirement's threshold, confirming the plan's recorded conditions still hold. That is a passing check, not the manual exception: the test-encoding rule governs behavioral criteria. A value measured under conditions the requirement does not describe is *partially met*, never **met** — name the missing condition, and propose moving the criterion to an `SC#` if nothing here can reproduce it.
   - **Stored-data requirements** — an `R#`/`E#` whose behavior depends on a change listed in the plan's **Data changes** also cites that the recorded migration/backfill command ran against the **Target** the plan names, its observed output, the plan's **Data integrity** check with its observed result (not just the command's exit), and the reversal where the plan recorded one, exercised with rows present. A run against a shared, staging, or production datastore is a stop-and-ask, never evidence the agent produces on its own. The report's `Data & delivery:` line carries the summary.
   - **Delivery-switched requirements** — where the plan's **Delivery** names a flag or config switch, evidence names the state it was produced under (which flag setting, which config value), the way a measured requirement names its run conditions; each state the feature ships in has its own evidence or an explicit Non-goal, and a state with neither is at best *partially met*. Where the plan records an off path, its exercised run (feature on → off → pre-feature behavior returns, plus what work survives the flip) goes on the report's `Data & delivery:` line, together with the stage the feature is at where the plan records **Rollout stages**.
   - **Third-party-backed requirements** — where an `R#`/`E#`'s behavior originates in a third party (a dependency call whose result the criterion asserts, or an external service the feature calls at runtime), its evidence names the stand-in the test ran against, as the plan's **Dependencies** line records it. A stand-in that line records with its contract tie, **or with the user's recorded acceptance of an untied one** (Recording gates → Stand-ins are tied or accepted here), *is* evidence — cite it and judge the requirement on it. Only where the plan records neither is the verdict capped at *partially met*: name the missing tie, and propose moving the criterion to an `SC#` naming where the real integration is exercised. A run against a live paid or production third-party account is a stop-and-ask, never evidence the agent produces on its own, exactly as for a shared datastore.
   - **Declared shortcuts** — a requirement whose implementation the implementer declared substandard ([clean-code.md](clean-code.md) → Declared shortcuts: a dated Decisions entry naming what was traded, the proper version, and its owner) is still **met** where the behavior ships and its test passes. List every such entry on the report's `Shortcuts declared:` line — the `T#`, what was traded, who owns the proper version — so the approver sees them at the gate rather than later in spec history.
   - **Reconcile the plan's bookkeeping** — the evidence just cited must sit in the component the plan's Requirement coverage table attributes this `R#`/`E#` to. Where it does not — the behavior was built elsewhere, or a `G#` fix landed in a component the row never named — amend that row and the component's **Implements** line to name where the code actually is, and bump `plan.md`'s `Last updated`. The table is checked here for *accuracy*, not merely presence as `scripts/validate.py` does; nothing else in this procedure reads it. *(Small features keep no plan — skip this.)*
3. **Assign a verdict per requirement.** Exactly one applies. Precedence where two fit: **spec drift** outranks *partially met* — classify the divergence first; and a failure step 4 attributed outside this change set takes a **blocked** verdict, never *not met*.

   | Verdict | Meaning |
   |---|---|
   | **met** | Behavior implemented; acceptance criteria encoded in a test case and assertion that executed and passed — or, where the user declined test tooling, in an approved manual check with its output cited |
   | **partially met** | Implemented but criteria not fully covered (missing edge case, missing test, an assertion that cannot observe the criterion) |
   | **not met** | Not implemented, or the verification fails for a cause inside this change set |
   | **blocked (pre-existing)** | The requirement's own evidence fails for a cause step 4 attributed outside this change set. Reported with that attribution, not gapped; does not block exit |
   | **blocked (flaky)** | The requirement's only evidence is nondeterministic on the untouched tree too (step 4). Reported with the runs that show it, not gapped; does not block exit — introduced flakiness is *not met*, never this |
   | **blocked (execution pending)** | Implementation complete and evidenced against the stand-in or rehearsal target the plan approves, but the requirement's own sanctioned evidence is a run only the user can perform — a migration or delivery step against a shared, staging, or production environment. Available only where a `- [!] Blocked` task on record names that run and the plan's **Target** / **Who executes it** line names the user; cite the stand-in evidence, that task, and what is still unrun. Not a gap, does not block exit, blocks the terminal **implemented** status, and is re-verified when the run happens |
   | **spec drift** | Code deliberately does something different from the spec |
   | **superseded** | Another feature's spec replaced this requirement — it carries `— superseded by …` in `spec.md`, annotated with the user's explicit sign-off; evidence is the successor's `R#`. Nothing is re-verified and no gap is filed |
   | **deferred** | Cut from this change set by a dated decision on record — the requirement carries `— deferred (Decisions YYYY-MM-DD, owner <who>)` in `spec.md` and an owner in the open-follow-through path ([team-and-review.md](team-and-review.md)). Evidence is that Decisions entry. Not verified, not a gap, never re-filed. Deferral needs the user's explicit sign-off, and a requirement inside the spec's **Minimum shippable** line cannot take this verdict — cutting into that set cancels the feature |

4. **Run the full verification suite** — every `Verify:` command from `tasks.md`, plus every quality gate recorded in `plan.md`. *(Small features: both live in the collapsed `spec.md`.)* Each gate **passes** when it shows no new failures against its recorded baseline.

   - **Attribute before calling a failure new.** Re-run the check on the current tree **and** with the feature's changes removed (stash, or a worktree at the recorded **Base**) — the base-tree control is not skipped on a hunch, and it leaves an artifact: **every failure gets its own entry on the report's mandatory `Attribution:` line, naming the base-tree command actually run and what it printed** (`pytest tests/test_ledger.py::test_lock — on 4d1e0aa worktree: 1 failed, same assertion`). No `blocked (pre-existing)` and no `blocked (flaky)` verdict exists without that line; unattributed is what a skipped control produces. Fails there too → `pre-existing`. Intermittent there → `flaky`: add it to the baseline as nondeterministic, say so in the report, never block on it. Reproduces at HEAD but never on repeated runs of the untouched tree → **new**, even when it only fails on some runs here: flakiness the feature introduced is a bug (concurrency `E#`s are where it hides), never a baseline entry.
   - **Where the tree cannot be reverted** — no VCS, `Base: — no resolvable history`, or another session's uncommitted work is present — skip the base-tree control, say so in the report, and treat the failure as `unattributed` rather than new. Never `git stash` a tree you did not author: a repo-global stash strands a concurrent session's in-progress work with no rule that would ever look for it.
   - **A failure classified `new` is a gap**, whichever gate found it and whether or not any `R#` covers the code it points at: file a `G#` over it, and it blocks exit exactly like a failed requirement. `unattributed` is reported to the user with what could not be ruled out, and blocks exit until they accept it.
   - Any baseline entry added during Phase 7 is written back into `plan.md` → Quality gates with the runs that justify it, and that artifact's `Last updated` bumped — the report alone is not the record.
   - Compare a baseline recorded as a count (a lint backlog too large to enumerate) per file and per rule, never by diffing line-anchored reports — an insert shifts every line below it and manufactures phantom hits.
   - **A gate whose command did not complete is not a passed gate, whatever its failure count** — it errored, crashed, exited on a configuration or dependency problem, or collected nothing to check. Zero findings from a run that never ran is not "no new failures": report it `pending` like an unrun pipeline gate, do not exit the convergence loop on it, and compare the run's own scope against the baseline's (files checked, rules loaded, tests selected), not only its failure count. A rise in the test gate's skipped count — or a drop in its executed or passing count — is a new failure, not a pass: a suite green because its tests were disabled, deleted, or loosened has verified nothing (step 2). Deleting or weakening a failing test is never how a gate passes: account for every pre-existing test this feature removed, disabled, or weakened on the report's `Tests removed:` line, and unless the removal is itself a behavior change an `R#` specifies, get the user's explicit sign-off.
   - List pre-existing failures flagged `pre-existing`; they may be proposed as a separate fix task with the user's approval and never block convergence. With no baseline recorded, reconstruct it on the pre-feature tree and say so in the report.
   - **Where the rebase test on the plan's Base line fires** (Recording gates), the baseline is stale: re-run the gates on the current merge base to refresh it, update the plan's **Base** SHA and branch name, and note the re-baseline in the report; failures the upstream introduced count as `pre-existing`.
   - A failure tracing to another feature's work is external the same way, committed or not: attribute it over the failing paths with `git log`/`git blame` first — if the change that introduced it is neither on this feature's branch nor `<slug>: `-prefixed (a sibling's commits on a shared branch, or its uncommitted edits here), flag it in the report for that feature's own Phase 7, treat it as `pre-existing`, add it to the baseline, and never block on it — or, while that work is uncommitted, ask the user to commit or stash it and re-run.
   - A gate the plan records as **pipeline-only** is evidenced by that pipeline's run on this change set — cite the run's identifier and result, judged by the same comparison; step 2's manual exception never covers it, because the check does run, just not here. Where no such run exists yet, report the gate `pending` and do not exit the convergence loop on it, unless the user explicitly accepts the pass without it, recorded as a Decisions entry in `spec.md`.
5. **Sweep the full diff for junk code** — one pass over the feature's change set (built as described in step 6), against the checklist in [clean-code.md](clean-code.md). Any hit is a gap, same as a failed requirement.
6. **Delete unused generated code** — everything the feature added must be reachable, or it goes:
   - **Build the inventory first** — the union of (a) every `Files` entry across the feature's `T#`/`G#` tasks and (b) the feature's change set, where the repo uses git:
     - *Own branch*: `git diff <base>...HEAD`, `<base>` being the **Base** SHA recorded in `plan.md` → Quality gates (Small: next to the gates in the collapsed `spec.md`). No Base recorded → ask the user for the last commit that predates this feature's work; never guess `main`.
     - *Slug-prefixed commits on a shared branch*: the commits whose **subject** begins `<slug>: ` (`git log --format='%H %s' <base>..HEAD | grep '^[0-9a-f]* <slug>: '`) and `git show` over exactly those — an unanchored search over full messages drags in commits that merely mention the slug in a body, and sibling slugs that begin with it (`billing` vs `billing-invoices`).
     - Both modes read committed history only: add the uncommitted work too (`git status --porcelain`, untracked files included, plus `git diff` against the base), since the feature's work is often still in the working tree when Phase 7 runs.

     Count only paths this feature's tasks or plan name, in every mode. Everything else stays out of the inventory and goes on the report's `Excluded from inventory:` line naming its owner: paths and commits another in-flight or landed feature's `specs/<slug>/` artifacts claim (find those specs with the overlap scan in [team-and-review.md](team-and-review.md), so an empty result means "none"), everything a merged sibling branch brought into `<base>...HEAD`, and unclaimed local state that lives in the tree year-round (personal config overrides, dumps, long-lived untracked scratch files). Never file a gap against an exclusion. But a change-set path that no task or plan names, that no other feature claims, and that is not unclaimed local state is a bookkeeping miss, never an exclusion: add it to the inventory **and** to its owning task's **Files** line — that is why Phase 5 requires one commit mode or the other. Where the two sources disagree, reconcile by reading the code; never delete on a diff line alone. With no git, no resolvable **Base**, or no reliable Files entries, say so in the report and scope the sweep to the paths the tasks name. Exempt from the reachability requirement: `specs/<slug>/*`, `docs/<slug>.md` and README/CHANGELOG edits, which step 7 verifies instead; and declarative infrastructure or configuration the project applies through its own tooling (Terraform modules, k8s manifests, pipeline and schema definitions), whose Evidence is the apply/validate command and the environment it targets, not an in-tree caller.
   - List every symbol, file, export, and dependency in that inventory.
   - For each one, confirm something actually reaches it, and cite that reacher as Evidence:
     - production code, or a test that verifies real behavior;
     - an **entry point** — a route, a CLI command, a public API, or a framework/config registration: a scheduled or queued job declared in configuration, a signal/event handler, a plugin or DI registry entry, an admin/router registration, any symbol named by dotted-path string in config. *Public API* means a surface this repo publishes to consumers it does not control (an exported package boundary, a released artifact's interface, a REST/CLI/queue contract) — never a language visibility keyword: `pub`, `public`, and Elixir's `def` alike are no evidence of reachability, so name the consumer or the publication boundary;
     - a **contract the runtime or compiler dispatches on** — a behaviour or interface callback on a registered module (OTP `handle_call`/`handle_info`/`terminate`), a trait/protocol/typeclass implementation, a lifecycle or operator hook (`Drop`, `Display`), derive-generated impls included — whose Evidence is the contract plus the registration or use site of the *type*, not a caller of the function;
     - a **runner that consumes it** — a recorded quality-gate command, the build, or the project's migration/seed runner.
   - Unreached by any of the above → file a gap task to **delete it** — code, its tests, its exports, and any dependency only it used. Deletion is the default, but never automatic: a deletion gap is implemented only after the user explicitly confirms it. It survives only where one of these holds, cited as its Evidence:
     - the user explicitly promotes it to a requirement in `spec.md`;
     - it implements a requirement the spec carries as `— deferred` — code named by a live requirement is not code reached by nothing, so the choice is the user's and is put to them explicitly: keep it, citing the deferral's Decisions entry and naming the kept paths on that entry so later passes do not re-file it, or delete it now and rebuild when the deferral comes due. Report the choice on the `Dead-code sweep:` line either way, so "kept for a deferred requirement" is a recorded state and never a silent one;
     - a component (`C#`) in another feature's or capability's **approved** `plan.md` names it (a sibling capability from the same Phase 0 split; find those plans with the overlap scan in [team-and-review.md](team-and-review.md), other branches included) — cite that `C#` instead of filing a deletion gap;
     - it sits on a surface this repo publishes outside the analyzed tree — a library artifact other repos consume, a sibling deployable, ops/admin/JMX tooling, or dispatch named in external or DB-held configuration — where the Evidence is that publication boundary, confirmed with the user.

     Dead-code tooling flags framework-registered symbols as unreached — check the registration, of the module or type as much as of the function itself, before filing. Every deletion gap states its scope of analysis in one line — what was actually searched (this tree, plus any registries or config sources read) — so `unreached` reaches the user as a bounded finding, never an unqualified fact.
   - Sweep the other direction too: a **pre-existing** symbol whose last caller this feature removed or rewrote is dead code the feature just created — file a deletion gap flagged `pre-existing`, so the user sees it reaches beyond the feature's own code. Dependencies the same way: a pre-existing third-party dependency whose last import this feature removed is dead weight, and a manifest entry is neither a symbol nor a path the tasks name, so nothing else collects it. Confirm no remaining importers, then file the gap over the manifest entry, the lockfile entry, any vendored copy, and any attribution file kept for it.
   - **Walk it code-to-spec as well**: behavior in the change set that something does reach but that traces to no `R#`/`E#` — and is not plumbing for one — is scope creep, and the spec wins. Same promote-or-delete choice as unreached code: file a gap to delete it, or have the user promote it through a `spec.md` amendment.
   - **Check the plan's Reuses and Duplicates lines**: new code in the change set that duplicates behavior an existing module already provided is a gap — file it to replace the new copy with a call to (or an extension of) the existing code, then let the dead-code sweep collect the copy. A duplication the plan's **Duplicates** line already declared and the approver accepted is not re-filed: cite that line and report it on the `Dead-code sweep:` line as a declared duplication, so it stays visible without reopening a settled decision.
   - Use the ecosystem's dead-code tooling where available (`knip`/`ts-prune`, `vulture`, `deadcode`, compiler warnings — which exempt exported items in library crates, so a silent build is no evidence either); confirm hits by reading before deleting, since dynamic dispatch and reflection produce false positives.
7. **Check the documentation** — `docs/<slug>.md` exists (Small features: the README or doc-comment update the depth rules allow counts as the doc artifact — check that instead), describes actual behavior, its examples run as written, and README/CHANGELOG were updated where applicable. An example that cannot execute here for the reason step 2's exception names is evidenced on the same terms: a manual check the user approved, cited with its observed output, never an unrun example reported as run. Missing or stale docs are a gap. Where the doc page must carry an **Operating** section ([implement.md](implement.md) → Phase 6 states the three conditions), it exists and matches what shipped; missing or stale, it is a documentation gap like any other. So is a Decisions entry that binds beyond this feature — an architecture pattern, a shared dependency, a cross-cutting convention, a targeted contract version — with no entry in the project's own decision record where the repo keeps one (`docs/adr/`, `decisions/`, an RFC folder).
8. **Walk the spec's Success criteria (`SC#`), then report.** Verify each `SC#` that is checkable now and cite its evidence; list the rest in the report as pending rollout checks — pending criteria inform the reader but do not block convergence. A pending `SC#` whose signal this feature itself produces is pending only on its *value*: verify the emission now — cite the signal appearing with the expected shape, from its test or an observed run here — and report the criterion as pending on that signal. A pending `SC#` that reads a signal nothing in the change set or the existing system produces is not pending but unverifiable: file it as a gap (`G#`), same as a *not met* requirement. *(Small features: the collapsed `spec.md` keeps no Success criteria section — skip the walk and write `Success criteria: none — no SC# at Small`.)*
9. **Check the change set's integration state, then close the report block.** Read the plan's **Integration** line (Small: next to the tasks in the collapsed `spec.md`). Where it records a review-gated path: is this change set merged into the branch the plan's **Base** names (`git merge-base --is-ancestor HEAD <that branch>`), and are the required approvals on record? Report the answer on the report's `Integration:` line — `merged (<identifier>)` with the approvals cited, `pending review (<identifier>)`, or `not opened yet` — together with any `pending sign-off: <role>` the spec's Status line carries. Where the line records `— direct commits to the base branch`, report `direct commits — no review policy`. Where **Base** has no resolvable history, report `Integration: — not checkable, no resolvable history`. A pending state informs the reader and blocks neither the report nor the convergence loop; it blocks only the terminal **implemented** status (Terminal status below). Then set the block's `Converged:` line and report it to the user. Any edit made to the change set after a converged pass — review fixes included — invalidates that pass's report, which its `Change set:` SHA makes checkable: run the procedure again. Rules in [team-and-review.md](team-and-review.md).

## Handling gaps

- **Approval and the waiver** — gaps are reported, then approved, then implemented via Phase 5. A standing waiver (SKILL.md core rule 2) covers that approval: gaps are still reported, just not blocked on. A gap whose resolution appears in a row of [sign-off.md](sign-off.md) is the exception; it needs the sign-off that row requires. Read the table row by row against each gap before implementing it. Never work from a remembered list of it.
- **Diagnostic passes** — when the pass runs with unchecked `T#`/`G#` tasks remaining (a resume drift check, regenerated artifacts, a reopened feature; `- [~] Waived` and `- [>] Deferred` are closed and never count as unchecked, and `- [!] Blocked` is open work but not unchecked work — it is exempt here as it is from Phase 7's entry condition, its requirements taking **blocked (execution pending)**), its verdicts are diagnostic, not a convergence attempt: file no `G#` for a verdict an existing unchecked task already covers — cite that task instead. Report the drift and partial verdicts and any refreshed baseline, mark the block `Converged: no — diagnostic`, then hand back to Phase 5 at the first unchecked task. On regenerated artifacts, a **met** verdict is what licenses checking that task's box.
- **not met / partially met**, and every gate failure step 4 classified `new` → append tasks (IDs `G1`, `G2`, …, same format as normal tasks, at the heading level the tasks template pins) to the `Gaps found in verification` section of `tasks.md` — for Small features, under the collapsed `spec.md`'s `## Tasks` section. `G#` numbering continues across passes and is never reused. Get approval, then implement via Phase 5.
- **spec drift** → decision point for the user, never yours alone:
  - If the code's behavior is *better*: amend `spec.md` (and its Decisions section) to match, with the user's approval.
  - If the spec was right: file a gap task to fix the code.
  - Either way, spec and code must agree when you finish.

## Convergence loop

After gap tasks are implemented, run the procedure again. Exit when a full pass yields **met** on every requirement and edge case (`R#`, `E#`) — except any the user accepted as a documented limitation, annotated as **superseded**, annotated as **deferred** by a dated decision naming its owner, or reported **blocked** with its attribution (step 4's `Attribution:` line, or the `- [!] Blocked` task for **blocked (execution pending)**) — **and** the gates show no new, unattributed, or incomplete-run failures against the recorded baseline, and the docs are accurate (step 7), with zero new gaps. Two consecutive passes that keep finding new gaps usually mean the spec is ambiguous — go back to Phase 2 rather than iterating blindly, and count the passes on the report blocks' `pass <n>` headings, which is what makes "two" checkable. If a requirement cannot reach *met* by any available means, stop the loop and put the choice to the user (accept it as a documented limitation, defer it with a date and an owner, change the spec, or add the missing tooling) — never keep re-running the pass on an unreachable verdict. An accepted limitation is recorded as a Decisions entry in `spec.md` **and** annotated on the requirement itself — `— accepted limitation (Decisions YYYY-MM-DD, accepted by <who>)`, the signer named the way a deferral names its owner — after which later passes report its recorded verdict and never re-file a gap for it. The agent never writes that annotation on the user's behalf: with the choice put and unanswered, the block reads `Converged: no — awaiting <the decision>` and the pass ends there (SKILL.md core rule 2). A gap the user declines to fix is closed as **waived**: record the choice and its rationale as a Decisions entry in `spec.md`, replace that `G#` task's `- [ ] Done` with `- [~] Waived — YYYY-MM-DD, why`, and list it in the report — a waived gap does not block exit and is never re-filed.

## Report format

**Write it as you go, not at the end.** Open the block at step 1 — heading (`… — pass <n>`, counting from 1 across the feature's passes and never restarting), `Change set:`, `Converged: no — in progress (step 1)` — and append each verdict row to `tasks.md` as you assign it, bumping the step number as you advance. Step 9 closes it by setting `Converged: yes | no` and filling the remaining labelled lines. A pass that runs out of context then leaves its verdicts on disk, and the next session restarts at the step the block names instead of at step 1 ([lifecycle.md](lifecycle.md) → Resuming work).

**Where the change set exceeds what one pass can read**, verify it in slices by component — one appended block per slice, each naming its slice on the `Change set:` line — and converge on the union: the feature is converged when every slice's last block reads `Converged: yes` against the same `Change set:` SHA.

**Every labelled line below is always present**; write `none` where there is nothing to report. An absent line is an unfinished pass, never an empty one.

## Terminal status

- Once the change set is merged into the branch the plan's **Base** names, set `spec.md` and `plan.md` to **implemented**. It means merged and verified *in the repo*, never that the feature is live.
- **Rollout unfinished.** Where the plan's **Delivery** records rollout stages the feature has not finished, say so on the spec's Status line: `implemented — rollout in progress, stage <the one it is at>`. Give the final stage a dated owner, the way an introduced flag carries a retirement owner. Reduce it to plain **implemented** when the last stage completes.
- **Blocked task.** A standing `- [!] Blocked` task qualifies the status the same way: `implemented — T4 blocked, <what the user must run>, owner <who>`. It reduces to plain **implemented** once that run lands and a pass re-verifies the requirements it evidences.
- `tasks.md` stays `approved`. Its checkboxes, completion notes and appended reports are its completion record. At Small, the collapsed `spec.md` takes the spec's status, and its `## Tasks` section is that record.
- A later feature that replaces this one marks the old spec and plan **superseded**, linking the successor, and the doc page **deprecated**. Never delete the history.

## Audit mode

The entry: a `spec.md` with shipped code but no `plan.md` and no `tasks.md`, and the user asks whether the code matches the spec. Re-read the spec, walk its `R#`/`E#` for evidence as step 2 says, and report the verdict table with what it would take to close each gap. There is no change set, so:

- **Confirm the path set before building the inventory.** A spec names behavior, never paths. Propose the path set, listing the registries and config sources read with it, and get the user's confirmation.
- **Neither `blocked` verdict is available.** Step 4 never runs, so every cause is outside a change set by construction, and a genuinely broken feature would file as not-our-problem. A failing check is *not met* or *partially met*.
- **Every `unreached` finding carries step 6's scope-of-analysis line.** Here it attaches to findings, not to deletion gaps; this mode files none.
- **Output:** the verdict table, then `Scope of analysis:` (the confirmed path set plus what else was read) and `Not run:` (the gates, baselines, controls and sweeps this mode skips). File no `G#`, append no report block, set no Status. The output is the report to the user. Turning it into work is a normal entry at Phase 1 or Phase 3.
