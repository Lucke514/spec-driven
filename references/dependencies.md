# Third-party dependencies

Rules for Phase 3 (Plan), used whenever a component needs code this project does not already have, changes the version of a dependency it does have, retires one, or calls an external service at runtime. Its output is the plan's **Dependencies** line (at Small, recorded next to the tasks in the collapsed `spec.md`). Discover what this project actually uses — manifest, lockfile, vendored directory, mirror or approved-list policy, dependency-scan gate, its own license — by reading the repo; record what exists and propose nothing uninvited. Adding a dependency, or changing the version of one other code shares, needs the user's explicit sign-off (core rule 2): they approve the vendor, not just the plan.

The line carries one row per dependency: its name, whether it is new / a version change (`from → to`) / retired, its exact resolved version, and the `R#`/`E#` that needs it. Each row answers the checklists below that apply to it.

## Adding a new dependency

- [ ] **Intake** — search before reaching outside: the manifest and lockfile for something the project already depends on that does this, and the source for an existing integration with the same provider (a client, a wrapper, another feature's adapter). A dependency already present that nearly fits is extended, exactly as internal code is under Phase 3's reuse-first rule; a second library doing what one already does needs a stated reason in the plan.
- [ ] **How it enters** — the project's own mechanism as read from the repo: manifest plus its committed lockfile, a vendored directory, a private mirror or approved list. Record the exact resolved version and pin it — never a floating range, and never a manifest edit without the lockfile update the project's own tooling produces. Where the policy requires a mirror or approval step this environment cannot perform, that step is the user's and is named here.
- [ ] **License** — the dependency's license as published, and whether it is compatible with how this repo is licensed and distributed (read the repo's own license and any policy file it keeps). An incompatible, missing, or unclear license is a stop-and-ask — never a guess, and never an assumption from the ecosystem's norm.
- [ ] **Maintenance** — when it last released, whether it carries open critical advisories, and — where the project already runs a dependency, license, or security scan (recorded in the plan's Quality gates) — that the gate passes with it added, judged by the same no-new-failures comparison. A dependency that is archived, unmaintained, or published by a single person names what happens if it stops (fork, vendor, replace) in the plan's Risks.
- [ ] **Weight & install-time behavior** — what it drags in (transitive count) and its effect on any size, bundle, or build-time budget the project already enforces (run that gate with it added, like any other); whether it runs install-time scripts, needs a native toolchain, or requires a runtime or platform version this project's pipeline does not have.
- [ ] **Cost & limits** — only where the dependency calls a metered, rate-limited, or credentialed external service: who pays, the quota or rate limit the feature must stay inside, and how its credential reaches every environment through the project's own mechanism ([data-and-delivery.md](data-and-delivery.md) → Configuration). What the feature does past that limit is behavior — an `R#`/`E#` in the spec, never a runtime surprise.

## Changing the version of an existing dependency

- [ ] **Blast radius** — enumerate this repo's other callers of that dependency (search the manifest and the import sites; in a monorepo, across every package that declares it), state what the version change does to them (changed behavior, removed or renamed surface, transitive bumps it forces), and name what covers them — their tests, or an explicit "not covered". Untested callers of the bumped dependency go in the plan's Risks with a stated mitigation.
- [ ] **Why now** — the `R#`/`E#` of *this* spec that needs the new version. A version change no requirement here needs is never a side effect of a feature: present it to the user before approval and propose it as its own spec discussion, the same way as a new architecture.

## Calling an external service at runtime

- [ ] **Contract version** — the provider's API or protocol version this integration is written against, named as the provider names it, and where it is set (a request header, the SDK version, the endpoint path). Where the provider publishes an end-of-support or deprecation date, the move is an open follow-through ([team-and-review.md](team-and-review.md) → Open follow-through) — the same rule as flag retirement, and for the same reason: no sweep in this skill will ever file it for you.
- [ ] **Stood in for by** — what the tests actually run against: a hand-written fake, a provider-published fixture or contract artifact, a recorded real response, the provider's sandbox, or the real service. State where that stand-in's shape comes from, and which check — if any — re-confirms it against the live contract, and how often. A stand-in this repo asserts alone, with nothing tying it to the provider's own contract, caps the requirement's verdict at *partially met* in Phase 7 ([verification.md](verification.md) step 2): plan the tie, or move the criterion to an `SC#` naming the environment where the real integration is exercised.
- [ ] **Failure behavior** — name the `R#`/`E#` Phase 1's Degradation and partial-failure items already wrote for this provider being slow, unavailable, or returning an unexpected shape ([writing-specs.md](writing-specs.md)). Nothing covering it is an amendment to raise now (core rule 2), not a runtime discovery.

## Retiring a dependency

- [ ] **Removal owner** — a dependency this feature replaces or stops using is removed by a `T#` here — the manifest entry, the lockfile entry, any vendored copy, and any attribution or notice file the project keeps for it — after confirming the manifest and the source hold no remaining importers. Where it must outlive the rollout (a dual-run or compatibility window), its removal is an open follow-through ([team-and-review.md](team-and-review.md) → Open follow-through).

Tasks: adding, upgrading, or removing a dependency is its own `T#`, ordered before the tasks that import it; its **Files** name the manifest, the lockfile, and any vendored path. Its **Verify** runs the project's own install/resolve command plus the dependency, license, or size gate where the project has one; its **Acceptance** is the exact version resolved and pinned in the lockfile — for a removal, no remaining importers — never that the command exited. The user's sign-off on the dependency happens at plan approval, before that task runs.
