# Data changes & delivery

Rules for Phase 3 (Plan), used whenever a component changes stored data or the feature needs more than a merge to reach users. Its outputs are the plan's **Data changes** and **Delivery** lines (at Small, recorded next to the tasks in the collapsed `spec.md`). Discover what this project actually uses — migration mechanism, pipeline, environments, flag system — by reading the repo; record what exists and propose nothing uninvited. Where something the change needs is genuinely absent, Phase 3's missing-tooling rule applies: propose the minimal setup, or record the user's refusal as a Decisions entry in `spec.md`.

## Stored-data checklist

When **Data changes** is not `— none`, the plan states each of these in one line per change:

- [ ] **Mechanism** — the project's own way of changing stored data, found by reading the repo (a migrations directory, a schema tool, ordered scripts, an ops runbook). If nothing exists and the change needs it, say so and propose the smallest thing that fits the project; never introduce a framework as a side effect of a feature.
- [ ] **Target** — the datastore each data-change command runs against, named as the project names it and discovered by reading the repo's own config (a disposable local instance, an ephemeral CI database, a restorable copy). A command whose target is shared, staging, or production is a stop-and-ask — never a command the agent runs on its own. **Where none of those three exists and none can be created here**, say that in the line rather than assuming one away (`— none exists; nothing here can rehearse this change`): it is the missing-tooling case, so propose the smallest thing that fits (a container, a scratch schema, a restored dump) or record the user's refusal as a Decisions entry. The change's task is then `- [!] Blocked` on the user's own run, Phase 5's rehearsal (forward → reversal → forward) is what that run must include, and its requirements take Phase 7's **blocked (execution pending)** verdict ([verification.md](verification.md) step 3) — never *met* on an unrehearsed command.
- [ ] **Reversal** — the exact command or step that undoes the change, or an explicit statement that it is irreversible (destructive or data-losing) with the user's sign-off recorded as a Decisions entry in `spec.md`. That sign-off is per-change (core rule 2) and names what makes recovery possible: the project's existing backup, export, or restore path as discovered by reading the repo, or an explicit "none exists".
- [ ] **Existing rows** — what happens to data already stored: backfill, default value, or "nothing to do, and why". A backfill states how it behaves when re-run (idempotency) and what a partial run leaves behind.
- [ ] **Required data** — data the feature needs present to function (reference or lookup rows, default configuration, a first-run record): how it reaches each environment through the project's own seeding mechanism as discovered, and what a re-run does (idempotency). The seed step is its own `T#`, ordered with the migration and verified by the same integrity check.
- [ ] **Compatibility during rollout** — what the currently running code does against the new data shape, and the new code against the old one, while both exist. Where the project deploys without downtime, split the change into additive-then-cleanup steps (add the new shape and write both, move readers, remove the old shape) instead of one breaking step; where it does not deploy that way, say so in one line and skip the split.
- [ ] **Volume** — whether the change rewrites or locks enough data for that to matter here. Unknown volume is a `[NEEDS CLARIFICATION]` for the user, never a guess.
- [ ] **Data integrity** — the check that proves the data survived, stated as a command or query whose result is decidable (row counts before and after, a checksum over the moved values, an invariant query that must return zero rows), run against a store holding data representative in *shape* of production, never an empty one. Where **Volume** says the change only behaves differently at production scale, the measured-criteria rule applies: that check moves to an `SC#` naming its environment and the signal it reads ([writing-specs.md](writing-specs.md)).
- [ ] **Data lifecycle** — where the spec's data-lifecycle `R#`/`E#` names an existing erasure, export, or retention path, a new store of personal or regulated data joins it: that change is a component here and a `T#`, never an assumption that the path already covers the new store.

Tasks: each data change is its own `T#`, ordered before the tasks that depend on it. Its **Verify** names the **Target** it runs against and runs the change forward, then its reversal with rows present, then forward again — or cites the recorded sign-off where the change is irreversible; its **Acceptance** is the **Data integrity** check's result, not that the command exited. A cleanup step that only lands in a later release is a task here only if it ships now; otherwise it is an open follow-through ([team-and-review.md](team-and-review.md) → Open follow-through) — the intermediate state's code (dual writes, compatibility shims) is live and reached, so Phase 7's dead-code sweep will never file this for you.

## Delivery checklist

When **Delivery** is not `— ships with the normal release`, the plan states each line below. The vocabulary is written for a flag-gated rollout; **for a one-time change that ships once and does not stay switchable** — a migration, a backfill, a data repair — read it in that register rather than inventing a flag to fit it: *How it reaches users* is who runs it, where, and in what order; *Rollout stages* is the batching or the single window; *How it is turned off* is the reversal the Stored-data checklist already records (or `— irreversible, recorded under Reversal`); *Flag retirement* is `— none` where no flag exists. A slot that genuinely does not apply says so in one line and names why, and is never left blank.

- [ ] **How it reaches users** — the project's existing pipeline and environments as discovered (name them as they are named in the repo), plus any ordered steps this feature adds.
- [ ] **Who executes it** — each delivery step (deploy, promotion between stages, flag change, config change) names the environment it acts on and who performs it. A step acting on a shared, staging, or production environment is a stop-and-ask — never a command the agent runs on its own (core rule 2) — exactly as for the stored-data **Target** above.
- [ ] **Rollout stages** — only when **How it reaches users** names an ordered or staged rollout: one line per stage giving its scope (share of traffic, cohort, or environment, as the project expresses it), how long it is observed, the signal read (the `SC#` Phase 1's Rollout-signal item already named — never a new one invented here), the condition to advance to the next stage, and the condition to roll back. An unknown threshold is a `[NEEDS CLARIFICATION]` for the user, never a guess. Phase 7 reports the stage the feature is actually at on its `Data & delivery:` line.
- [ ] **Configuration** — for each new config value or secret the feature needs: how it reaches every environment the feature runs in, through the project's own mechanism as discovered; whether it is required or has a safe default; and the `R#`/`E#` Phase 1's Configuration item already wrote for its absence — never a new requirement invented here; nothing covering it is an amendment (core rule 2), not a runtime discovery. Its `T#` is ordered before the step that ships the code reading it. A value the feature needs that no environment has yet is a `[NEEDS CLARIFICATION]` for the user.
- [ ] **How it is turned off** — the flag, config value, or revert that disables the feature without shipping a code fix; or an explicit "no kill switch — reverting the release is the only path". The off path is exercised, not asserted: a `T#` turns the feature on, turns it off, and confirms the pre-feature behavior returns, and its line states what work already done under the on path survives the flip (compensation, reconciliation, or "nothing to undo").
- [ ] **Flag retirement** — a flag this feature introduces is owned from the moment it is planned: either a `T#` in this feature removes it, or it is an open follow-through ([team-and-review.md](team-and-review.md) → Open follow-through). Phase 7's dead-code sweep runs while the flag is still reached, so it will never file this for you.
- [ ] **Where the checks are measured** — each `SC#` that can only be observed after rollout names the environment it is measured in **and the signal it reads** (metric, log, dashboard, report), so Phase 7 reports it as pending *there* rather than as unverifiable. Where this feature must produce that signal, emitting it is a component in this plan and a `T#` here — never an assumption that something already emits it.
